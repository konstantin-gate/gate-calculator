**Дата:** 2026-07-07  
**Автор:** MiMoCode  
**Статус:** Финальный анализ

---

## Часть 1: Полный детальный план

### 1. Описание проблемы

При вводе выражения `4*(2+3)` и нажатии `)` калькулятор отображает ошибку `errors.doubleOperator` вместо вычисления результата `20`.

**Воспроизведение:**
1. Запустить калькулятор
2. Ввести `4`
3. Нажать `*`
4. Нажать `(`
5. Ввести `2+3`
6. Нажать `)`
7. **Ожидаемый результат:** вычисление `20`
8. **Фактический результат:** ошибка `doubleOperator`

---

### 2. Корневая причина

Баг находится в файле `Tokenizer.swift`, в методе `validateTokenSequence`.

**Проблемный код (строки 369-376):**
```swift
private func isOperatorOrLeftParen(_ token: Token) -> Bool {
    switch token {
    case .binaryOperator, .unaryMinus, .leftParenthesis:
        return true
    default:
        return false
    }
}
```

**Вызывающий код (строки 329-335):**
```swift
case .binaryOperator:
    let prevIsOp = i > tokens.startIndex && isOperatorOrLeftParen(tokens[i - 1])
    let nextIsOp = i + 1 < tokens.endIndex && isOperatorOrLeftParen(tokens[i + 1])
    let nextIsUnaryMinus = i + 1 < tokens.endIndex && tokens[i + 1] == .unaryMinus
    if prevIsOp || (nextIsOp && !nextIsUnaryMinus) {
        throw CalculatorError.doubleOperator
    }
```

**Механизм ошибки:**
- При вводе `4*(2+3)` токенизатор создаёт последовательность: `4`, `*`, `(`, `2`, `+`, `3`, `)`
- При валидации токена `*` (binaryOperator) проверяется `nextIsOp` — следующий токен `(`, то есть `.leftParenthesis`
- Метод `isOperatorOrLeftParen` возвращает `true` для `.leftParenthesis`
- Переменная `nextIsOp` становится `true`
- Токен `(` не является `.unaryMinus`, поэтому `!nextIsUnaryMinus = true`
- Условие `nextIsOp && !nextIsUnaryMinus` выполняется → выбрасывается `doubleOperator`

**Корень:** метод `isOperatorOrLeftParen` считает скобку оператором, хотя она им не является. Для проверки `nextIsOp` нужно различать операторы и скобки.

---

### 3. Анализ подхода Qwen36 (Plan A)

**Подход:** Полное удаление `.leftParenthesis` из `isOperatorOrLeftParen`.

**Преимущества:**
- Максимально простое изменение (удаление одной строки)
- Корректно устраняет корневую причину для данной проверки

**Недостатки:**
- Изменяет поведение **всех 5 мест вызова** `isOperatorOrLeftParen`, хотя неправильна только проверка `nextIsOp` (строка 331)
- Выражения типа `(+5` (скобка перед унарным минусом) перестают ловиться на уровне токенизатора — теперь они будут пойманы парсером с ошибкой `invalidExpression("Invalid expression")` вместо `doubleOperator`. Это **изменение поведения**, хотя результат для пользователя одинаков (ошибка).
- Название метода `isOperatorOrLeftParen` становится некорректным (метод больше не проверяет скобку)

**Найденная ошибка в анализе Qwen36:**
> Утверждение: "isOperatorOrLeftParen вызывается из одного места"
>
> Реальность: метод вызывается в **5 местах** (строки 330, 331, 338, 347, 358) — все в `validateTokenSequence`. Это критическая неточность в анализе.

---

### 4. Анализ подхода MiMoCode (Plan B)

**Подход:** Добавление нового метода `isOperatorOnly` и замена им вызова `isOperatorOrLeftParen` **только** в проверке `nextIsOp` (строка 331).

**Преимущества:**
- Хирургическая точность — затрагивает только единственную неверную проверку
- Полностью сохраняет поведение всех остальных 4 мест вызова `isOperatorOrLeftParen`
- Названия методов остаются осмысленными
- Проверки `prevIsOp` по-прежнему корректно ловят `(` перед операторами (например, `(+5` всё ещё поймается на уровне токенизатора)

**Недостатки:**
- Добавляет ~8 строк кода (новый метод)
- Существуют два похожих метода (`isOperatorOrLeftParen` и `isOperatorOnly`), что может сбивать

**Найденная ошибка в анализе MiMoCode:**
> Утверждение: "TestRunner падает на строке 139 из-за `5*-3`"
>
> Реальность: это **неверно**. Текущий код корректно обрабатывает `5*-3`:
> - `nextIsOp` проверяет следующий токен `.unaryMinus` → `true`
> - `nextIsUnaryMinus` тоже `true`
> - `!nextIsUnaryMinus = false`
> - Условие `nextIsOp && !nextIsUnaryMinus` = `true && false` = `false` → пропускается
>
> TestRunner может падать на строке 139 по другим причинам, но **не** из-за этого бага.

### 6. Итоговое решение

**Рекомендуется Plan B (хирургический подход MiMoCode).**

**Обоснование:**
- Plan B затрагивает только единственный неверный вызов (строка 331), сохраняя поведение всех остальных
- Plan A меняет поведение 4 других мест вызова, хотя они работают корректно
- При близком анализе Plan A создаёт **изменение поведения** для выражений `(+5` и `4*(+3)` — эти ошибки теперь ловятся на более позднем этапе (парсер вместо токенизатора). Хотя для пользователя результат одинаков (ошибка), это усложняет отладку и тестирование
- Дополнительные 8 строк кода — минимальная цена за полную сохранность существующего поведения

### 8. Верификация после изменений

| Выражение | Ожидаемый результат | Обоснование |
|---|---|---|
| `4*(2+3)` | `20` (вычисление) | Основной баг — должен работать |
| `5++3` | `doubleOperator` (ошибка) | `prevIsOp` на строке 330 ловит второй `+` |
| `(+5` | `doubleOperator` (ошибка) | `prevIsOp` на строке 330: `(` перед `+` → `isOperatorOrLeftParen` = `true` |
| `5*-3` | Пропускает валидацию | `nextIsOp=true`, `nextIsUnaryMinus=true`, `!nextIsUnaryMinus=false` → условие ложно |
| `4*(+3)` | `doubleOperator` (ошибка) | `prevIsOp` на строке 338: `(` перед `+` → `isOperatorOrLeftParen` = `true` |
| `(2+3)*4` | Пропускает валидацию | `prevIsOp` для `*`: проверяет `)` → `isOperatorOrLeftParen` = `false` → OK |
| `4*(2+3)*2` | `40` (вычисление) | Аналогично `4*(2+3)`, `*` после `)` не вызывает проблем |
| `((2+3))` | `5` (вычисление) | `prevIsOp` для второй `(` проверяет первую `(` → `true` → ожидается ошибка? Нет — `prevIsOp` только для `binaryOperator` |

> **Важно о `((2+3))`:** Проверка `prevIsOp` стоит только в блоке `case .binaryOperator`. Для `.leftParenthesis` такой проверки нет. Поэтому вложенные скобки работают корректно.
