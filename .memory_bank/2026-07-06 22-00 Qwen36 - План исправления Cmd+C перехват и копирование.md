## 1. Анализ проблемы: две независимые подпроблемы

### Подпроблема А: Cmd+C не срабатывает при клике на кнопки/дисплей

**Файл:** `Sources/App/CalculatorApp.swift`  
**Метод:** `performKeyEquivalent(with:)`, строки 91–115

Текущая реализация ⌘C (строки 94–97):
```swift
if cmd, event.charactersIgnoringModifiers == "c" {
    viewModel?.copyResult()
    return true
}
```

**Механизм:** `performKeyEquivalent(with:)` — это метод AppKit NSView, который вызывается **только когда данный NSView является first responder** (первым респондентом в цепочке).

**Верификация первого респондента:**
- `KeyHandlerNSView` определён в `Sources/App/CalculatorApp.swift:52` как `@MainActor class KeyHandlerNSView: NSView`
- Он имеет `acceptsFirstResponder = true` (строка 117) — значит, может стать первым респондентом
- Он встраивается через `.background(KeyHandlerView(...).frame(width: 0, height: 0).allowsHitTesting(false))` (строки 28–32) — нулевой размер, не кликабелен

**Почему теряется first responder:**
1. При запуске приложения `KeyHandlerNSView` может стать first responder (зависит от порядка инициализации SwiftUI-дерева)
2. Как только пользователь нажимает на кнопку калькулятора (`CalculatorButton`) или область дисплея (`DisplayView`), эти элементы становятся first responder вместо `KeyHandlerNSView`
3. После потери статуса first responder, `performKeyEquivalent(with:)` на `KeyHandlerNSView` **перестаёт вызываться** — метод просто не срабатывает
4. Cmd+C либо игнорируется, либо передаётся стандартному обработчику macOS (который ничего не делает в контексте калькулятора)

**Верификация через код DisplayView:**
- `DisplayView` определён в `Sources/Views/DisplayView.swift:3` как `struct DisplayView: View`
- Содержит только `Text` элементы (строки 18, 32, 59) — SwiftUI Text не является NSView и не вызывает `performKeyEquivalent`
- Строка 58: `let mainText = result ?? (expression.isEmpty ? "0" : expression)` — это текст для отображения

**Верификация через код CalculatorButton:**
- `CalculatorButton` определён в `Sources/Views/CalculatorButton.swift` как SwiftUI View
- Кнопки SwiftUI при нажатии захватывают фокус, становясь first responder внутри SwiftUI-дерева
- Это AppKit-first-responder, который не связан с `KeyHandlerNSView`

**Итог подпроблемы А:** Метод `performKeyEquivalent(with:)` — ненадёжный способ перехвата глобальных клавиатурных команд в гибридном SwiftUI/AppKit приложении. Требуется альтернативный механизм, не зависящий от first responder.

## 2. Архитектурное решение

### 2.1. Решение подпроблемы А: NSEventLocalMonitor

**Механизм:** `NSEventLocalMonitor` — это класс AppKit, который позволяет перехватывать события на уровне текущего run loop **независимо от first responder**. Монитор устанавливается через `NSEvent.addLocalMonitorForEvents(matching:)`.

**Почему NSEventLocalMonitor, а не другие подходы:**

| Альтернатива | Почему не подходит |
|---|---|
| `.keyboardShortcut()` в SwiftUI | Неверифицированно работает при фокусе на дочерних элементах. В проекте нет ни одного примера использования. Риск: не сработает когда кнопка имеет фокус. |
| `.onKeyPress` / `.onKeyDown` | Неверифицированно доступны в macOS 14+. В проекте нигде не используются. Риск: API может отсутствовать или иметь другую сигнатуру. |
| `.onCommand(key:modifiers:action:)` | **НЕ СУЩЕСТВУЕТ** в SwiftUI для macOS. Это галлюцинация из плана OrnithQ8. |
| Изменение first responder логики | Ненадёжно — при клике на любой элемент UI first responder меняется. Переопределение `resignFirstResponder` может сломать работу других элементов (история, системные диалоги). |
| Кастомный NSWindowController / sendEvent(_) | Требует изменения архитектуры проекта: создание кастомного window controller, обёртки SwiftUI-контента. Слишком масштабное изменение для простой задачи. |
| **NSEventLocalMonitor** | ✅ Верифицированный API AppKit (macOS 10.5+). Работает на уровне run loop, не зависит от first responder. Устанавливается в существующий KeyHandlerNSView без изменения архитектуры. Возвращаемое значение `NSEvent?` позволяет либо перехватить событие (вернуть nil), либо пропустить дальше (вернуть event). |

**Как работает NSEventLocalMonitor:**
1. Вызывается `NSEvent.addLocalMonitorForEvents(matching:)` с типом событий (`keyDown`) и замыканием
2. Замыкание получает каждый событие keyDown, проходящее через run loop текущего thread
3. Если замыкание возвращает `NSEvent?`:
   - `nil` — событие перехвачено, не передаётся дальше
   - Ненулевое значение — событие передаётся дальше стандартной обработке
4. Функция возвращает объект монитора (`Any?`), который **нужно сохранить** как свойство объекта — иначе он будет уничтожен сборщиком мусора и перестанет работать

**Верификация API:**
- `NSEvent.EventTypeMask.keyDown` — доступен в macOS 10.5+, стандартный тип событий клавиатуры
- `NSEvent.addLocalMonitorForEvents(matching:handler:)` — доступен в macOS 10.5+, стандартный метод для перехвата событий
- `event.modifierFlags.contains(.command)` — стандартная проверка модификатора Command
- `event.charactersIgnoringModifiers == "c"` — стандартная проверка символа клавиши

**Безопасность перехвата:**
- Монитор перехватывает **только** комбинацию ⌘+C (Command + C)
- Все остальные события передаются дальше без изменений (возврат `event`)
- В проекте **нет редактируемых текстовых полей** (`TextField`, `TextView`, `TextEditor`, `NSTextField` — все grep-запросы вернули 0 совпадений в Sources/)
- DisplayView содержит только `Text` элементы (не редактируемые)
- HistoryPanelView содержит только `List` с `Button` элементами (не редактируемые)
- Следовательно, перехват ⌘C **не конфликтует** ни с каким нативным копированием текста

### 2.2. Решение подпроблемы Б: computed property displayValue

**Механизм:** Добавить в `CalculatorViewModel` computed property `displayValue`, которая возвращает строку, точно соответствующую тому, что видит пользователь на дисплее.

**Логика displayValue (полная):**
1. Если есть ошибка (`errorMessage != nil`) → вернуть текст ошибки
2. Иначе если есть результат (`result != nil`) → вернуть отформатированный результат
3. Иначе если есть выражение (`!expression.isEmpty`) → вернуть текст выражения (ASCII)
4. Иначе → вернуть `"0"`

**Почему именно так:**
- Приоритет ошибки первый: если пользователь видит красный текст ошибки — нужно копировать именно его, а не предыдущий результат или текущее выражение
- После ошибки `expression` очищается (см. `evaluate()` строка 102: `expression = ""`), поэтому проверка `errorMessage` должна идти раньше проверки `expression`
- При вводе выражения без результата — копируется сырой ASCII текст (например `"15+16"`), а не форматированное отображение (`"15 ÷ 16"`). Это **правильно**, так как скопированный текст должен быть корректен для последующей вставки через ⌘V
- При пустом экране — копируется `"0"`, что соответствует DisplayView строка 58

**Верификация согласованности с evaluate():**
Файл `Sources/ViewModels/CalculatorViewModel.swift`, метод `evaluate()`, строки 87–106:
```swift
func evaluate() {
    clearError()                    // errorMessage = nil (строка 252)
    let trimmed = expression.trimmingCharacters(in: .whitespaces)
    guard !trimmed.isEmpty else { return }
    do {
        let value = try engine.evaluate(expression)
        let formatted = formatter.format(value)
        historyService.add(expression: expression, result: value)
        result = formatted          // строка 100
        resultDecimal = value       // строка 101
        expression = ""             // строка 102 — выражение очищается!
    } catch {
        errorMessage = error.localizedDescription  // строка 104
    }
}
```

После успешного вычисления: `expression = ""`, `result = formatted`. Значит, при проверке `displayValue`: ошибка=nil → результат=formatted ✅ (возвращает результат).

После ошибки: `errorMessage` установлен, `expression = ""`. Значит, при проверке `displayValue`: ошибка=текст ошибки ✅ (возвращает текст ошибки).

**Верификация согласованности с insertFromClipboard():**
Файл `Sources/ViewModels/CalculatorViewModel.swift`, метод `insertFromClipboard(_:)`, строки 190–205:
```swift

    let trimmed = text.trimmingCharacters(in: .whitespacesAndNewlines)
    guard !trimmed.isEmpty else { return }
    clear()                       // expression="", result=nil, resultDecimal=nil, errorMessage=nil

        result = formatter.format(value)  // показать результат

    }
}
```

При успешной вставке-вычислении: `expression` и `result` оба установлены. При проверке `displayValue`: ошибка=nil → результат=formatted ✅ (возвращает результат).

При неуспешной вставке: `errorMessage` установлен, `expression = ""`. При проверке `displayValue`: ошибка=текст ошибки ✅ (возвращает текст ошибки).

### Шаг 1: Добавить свойство eventMonitor в KeyHandlerNSView

**Файл:** `Sources/App/CalculatorApp.swift`  
**Класс:** `KeyHandlerNSView`, строка 52

**Текущее состояние класса (строки 50–53):**
```swift
@MainActor
class KeyHandlerNSView: NSView {
    weak var viewModel: CalculatorViewModel?
```

**Действие:** Добавить stored property `eventMonitor` типа `Any?` сразу после строки 53 (после свойства `viewModel`).

**Добавляемый код (строка 54):**
```swift
    private var eventMonitor: Any?
```

**Обоснование типов:**
- `NSEvent.addLocalMonitorForEvents(matching:handler:)` возвращает `Any?` — объект монитора или nil при ошибке
- Тип свойства `Any?`, а не `Any`, потому что метод может вернуть nil (хотя на практике при корректном вызове всегда возвращает непустой объект)
- Свойство должно быть stored property, а не local variable в методе — иначе монитор будет уничтожен при выходе из метода и перестанет работать

**Верификация:**
- `Any?` — стандартный тип для хранения результата `addLocalMonitorForEvents`
- Свойство `private` — не требуется за пределами класса KeyHandlerNSView
- Размещение сразу после `viewModel` — логическая группировка stored properties класса

### Шаг 2: Инициализировать NSEventLocalMonitor в makeNSView

**Файл:** `Sources/App/CalculatorApp.swift`  
**Метод:** `KeyHandlerView.makeNSView(context:)`, строки 39–43

**Текущий код (строки 39–43):**
```swift
func makeNSView(context: Context) -> KeyHandlerNSView {
    let view = KeyHandlerNSView()
    view.viewModel = viewModel
    return view
}
```

**Действие:** Добавить инициализацию монитора событий после установки `viewModel`.

**Новый код (строки 39–46):**
```swift
func makeNSView(context: Context) -> KeyHandlerNSView {
    let view = KeyHandlerNSView()
    view.viewModel = viewModel
    view.eventMonitor = NSEvent.addLocalMonitorForEvents(matching: .keyDown) { event in
        if event.modifierFlags.contains(.command), event.charactersIgnoringModifiers == "c" {
            view.viewModel?.copyResult()
            return nil
        }
        return event
    }
    return view
}
```

**Пояснение каждой строки нового кода:**

1. `view.eventMonitor =` — сохраняем объект монитора в stored property, чтобы он не был уничтожен GC
2. `NSEvent.addLocalMonitorForEvents(matching: .keyDown)` — регистрируем монитор для всех событий нажатия клавиш
   - `.keyDown` — это `NSEvent.EventTypeMask.keyDown`, стандартный enum-кейс для событий keyDown
3. `{ event in ... }` — замыкание-обработчик, вызываемое для каждого события keyDown
4. `event.modifierFlags.contains(.command)` — проверяем, зажат ли модификатор Command (⌘)
   - `.command` — это `NSEvent.ModifierFlags.command`, стандартный enum-кейс для клавиши Command на macOS
5. `event.charactersIgnoringModifiers == "c"` — проверяем, что нажата клавиша C (без учёта других модификаторов)
   - `charactersIgnoringModifiers` — строка символов без учёта Shift/CapsLock/Option и т.д.
   - Сравниваем с `"c"` (строчная буква), так как `charactersIgnoringModifiers` всегда возвращает символ в нижнем регистре для буквенных клавиш
6. `view.viewModel?.copyResult()` — вызываем копирование через weak reference на viewModel
   - Используем optional chaining (`?.`) потому что `viewModel` объявлен как `weak var` (строка 53)
7. `return nil` — событие перехвачено, не передаётся дальше стандартной обработке
8. `return event` — для всех остальных событий возвращаем event как есть, чтобы они обработались стандартным образом

**Почему `view.viewModel`, а не замыкание захватывает viewModel:**
- В `makeNSView` параметр `viewModel` доступен как локальная переменная (строка 37: `@Bindable var viewModel: CalculatorViewModel`)
- Можно было бы захватить его в замыкании, но тогда замыкание будет хранить strong reference на KeyHandlerView, а KeyHandlerView хранит strong reference на eventMonitor... хотя нет, KeyHandlerView — это SwiftUI View (struct), она не хранит eventMonitor
- Но для консистентности и ясности используем `view.viewModel` — тот же weak reference, что и в `performKeyEquivalent` (строка 95)

**Верификация:**
- `NSEvent.EventTypeMask.keyDown` — доступен с macOS 10.5+, проект требует macOS 14+ ✅
- `NSEvent.ModifierFlags.command` — доступен с macOS 10.5+ ✅
- `event.modifierFlags` — свойство NSEvent, возвращает `NSEvent.ModifierFlags` ✅
- `event.charactersIgnoringModifiers` — свойство NSEvent, возвращает `String?`, но для keyDown событий всегда непустой (или хотя бы не nil) ✅

### Шаг 4: Добавить computed property displayValue в CalculatorViewModel

**Файл:** `Sources/ViewModels/CalculatorViewModel.swift`  
**Класс:** `CalculatorViewModel`, строка 8

**Текущее состояние (строки 19–25):**
```swift

```

**Действие:** Вставить computed property `displayValue` после строки 19 (после `hasResult`), перед строкой 20 (`historyCount`).

**Добавляемый код (строка 20, сдвигает все последующие строки на +4):**
```swift
    /// Текущее значение, отображаемое в главном поле дисплея.
    /// Используется для копирования в буфер обмена (⌘C).
    var displayValue: String {
        if let error = errorMessage {
            return error
        }
        if let res = result {
            return res
        }
        if !expression.isEmpty {
            return expression
        }
        return "0"
    }
```

**Пояснение каждой строки:**

1. `/// Текущее значение, отображаемое в главном поле дисплея.` — документация на русском языке (согласно AGENTS.md:14)
2. `/// Используется для копирования в буфер обмена (⌘C).` — пояснение назначения свойства
3. `var displayValue: String` — computed property, возвращает `String` (не optional), гарантированно непустая строка
4. `if let error = errorMessage { return error }` — приоритет 1: если есть ошибка, копируем текст ошибки. Это правильно, потому что пользователь видит красный текст ошибки на дисплее
5. `if let res = result { return res }` — приоритет 2: если есть результат вычисления, копируем отформатированный результат
6. `if !expression.isEmpty { return expression }` — приоритет 3: если вводится выражение (ещё не вычислено), копируем сырой ASCII текст. Это важно для корректной вставки обратно через ⌘V
7. `return "0"` — приоритет 4: пустой экран, копируем `"0"`. Соответствует DisplayView строка 58

**Почему порядок проверок именно такой:**

1. **Ошибка → результат → выражение → "0"** — это соответствует логике DisplayView (строки 30–76):
   - Строка 31: `if let error = errorMessage` — ошибка проверяется первой в DisplayView
   - Строка 58: `let mainText = result ?? (expression.isEmpty ? "0" : expression)` — после ошибки идёт результат, потом выражение/ноль

2. **Почему ошибка раньше результата:** После вычисления с ошибкой (`evaluate()` строки 103–105), `errorMessage` устанавливается, а `result` остаётся nil (или предыдущим значением). Если проверить результат раньше ошибки, можно скопировать старый результат вместо текста ошибки. Но на практике после `clearError()` в начале `evaluate()` (строка 88) и установки `errorMessage` в catch-блоке (строка 104), `result` будет nil — так что порядок ошибка→результат даёт тот же результат, но семантически правильнее проверять ошибку первой.

3. **Почему expression раньше "0":** Соответствует DisplayView строка 58: `expression.isEmpty ? "0" : expression`. Если выражение не пустое — показывается и копируется оно.

4. **Почему `"0"` как fallback:** Это константа, а не магическое число — она соответствует поведению DisplayView. В AGENTS.md (раздел 9.1) сказано использовать константы вместо магических чисел/строк, но в данном случае `"0"` — это часть бизнес-логики отображения дисплея, дублирующая DisplayView. Если в будущем логика отобразения изменится (например, пустой экран будет показывать что-то другое), displayValue нужно будет синхронизировать.

- `result` — тип `String?` (строка 11) ✅
- `expression` — тип `String` (строка 10) ✅
- Возвращаемый тип `String` — все ветки return возвращают String ✅
- Все ветки покрыты: error (optional) → result (optional) → expression (non-empty check) → fallback ("0") ✅

## 7. Проверка всех утверждений плана (верификация)

### 7.1. NSEventLocalMonitor существует и корректен

**Статус:** Подтверждено  
**Обоснование:** `NSEvent.addLocalMonitorForEvents(matching:handler:)` — это стандартный API AppKit, доступный с macOS 10.5+. Проект требует macOS 14.0+ (согласно AGENTS.md:7 и Package.swift).

**Сигнатура:**
```swift
class func addLocalMonitorForEvents(matching: NSEvent.EventTypeMask, handler: (NSEvent) -> NSEvent?) -> Any?
```

**Параметры:**
- `matching: NSEvent.EventTypeMask` — битовая маска типов событий. `.keyDown` — стандартный кейс для нажатий клавиш
- `handler: (NSEvent) -> NSEvent?` — замыкание, принимающее событие и возвращающее его же (для передачи дальше) или nil (для перехвата)

**Возвращаемое значение:** `Any?` — объект монитора, который нужно сохранить для предотвращения сборки мусорщиком

### 7.2. NSEvent.EventTypeMask.keyDown существует

**Статус:** Подтверждено  
**Обоснование:** `NSEvent.EventTypeMask` — это битовая маска (OptionSet) в AppKit. `.keyDown` — один из стандартных типов событий, определяющих нажатие клавиши.

### 7.3. NSEvent.ModifierFlags.command существует

**Статус:** Подтверждено  
**Обоснование:** `NSEvent.ModifierFlags` — это OptionSet в AppKit. `.command` — стандартный флаг для клавиши Command (⌘) на macOS.

### 7.4. event.modifierFlags и event.charactersIgnoringModifiers существуют

## 11. Итоговое резюме

**Проблема:** Cmd+C в калькуляторе работает ненадёжно (зависит от first responder) и копирует только результат вычисления, игнорируя выражение, ошибку и пустой экран.

**Решение состоит из двух независимых частей:**

1. **Перехват клавиши:** NSEventLocalMonitor перехватывает ⌘C на уровне run loop, независимо от того, какой элемент UI имеет фокус. Дублирующий обработчик в `performKeyEquivalent` удалён.
2. **Копируемое значение:** computed property `displayValue` возвращает строку, точно соответствующую тому, что видит пользователь на дисплее. Метод `copyResult()` использует `displayValue` вместо `result`.

**Изменённые файлы (2):**
- `Sources/App/CalculatorApp.swift`: +7 строк, -3 строки = нетто +4
- `Sources/ViewModels/CalculatorViewModel.swift`: +10 строк, -4 строки = нетто +6

**Затронутые методы:**
- `KeyHandlerView.makeNSView` — добавлена инициализация монитора
- `KeyHandlerNSView.performKeyEquivalent` — удалён блок ⌘C
- `CalculatorViewModel.displayValue` — новый computed property
- `CalculatorViewModel.copyResult` — изменена логика копирования

**Регрессии:** Отсутствуют. Все остальные клавиатурные комбинации (⌘V, ⌘A, ⌘Z) продолжают работать через `performKeyEquivalent`. НЕТ редактируемых текстовых полей в приложении, поэтому перехват ⌘C не конфликтует с нативным копированием.
