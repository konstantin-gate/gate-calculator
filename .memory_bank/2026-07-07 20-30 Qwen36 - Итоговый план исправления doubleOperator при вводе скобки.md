## ЧАСТЬ 1. КРАТКОЕ РЕЗЮМЕ ПОЗИЦИЙ (без кода и примеров)

### План Qwen36 (2026-07-07 19-48)

- **Корневая причина:** метод `isOperatorOrLeftParen` возвращает `true` для `.leftParenthesis`, из-за чего валидатор ошибочно классифицирует комбинацию «бинарный оператор + открывающая скобка» как двойной оператор.
- **Решение:** удалить `.leftParenthesis` из списка случаев метода `isOperatorOrLeftParen`. Функция будет возвращать `true` только для `.binaryOperator` и `.unaryMinus`.
- **Объём изменений:** одна строка — удаление одного кейса из switch.
- **Побочные эффекты:** изменение влияет на все четыре места использования `isOperatorOrLeftParen` внутри `validateTokenSequence`, но ни один корректный сценарий не ломается.

### План MiMoCode (2026-07-07 20-05)

- **Корневая причина:** та же — метод `isOperatorOrLeftParen` включает `.leftParenthesis`, что приводит к ложному срабатыванию при проверке следующего токена после бинарного оператора.
- **Решение:** создать новый приватный метод `isOperatorOnly`, который проверяет только операторы (без скобок), и использовать его исключительно в строке проверки `nextIsOp` внутри кейса `.binaryOperator`.
- **Объём изменений:** добавить новый метод (~7 строк) + заменить одну строку вызова.
- **Побочные эффекты:** изменение затрагивает только один конкретный check — nextIsOp для binaryOperator. Все остальные проверки остаются без изменений.

## ЧАСТЬ 2. СРАВНИТЕЛЬНЫЙ АНАЛИЗ

### Достоинства плана Qwen36

1. Максимально простое решение — одна строка удалена.
2. Глубокий анализ корневой причины с пошаговой подстановкой конкретных значений переменных.
3. Подробная верификация всех четырёх кейсов валидации (binaryOperator, percent, unaryMinus, rightParenthesis).
4. Чёткое объяснение архитектурной ошибки: объединение двух семантически разных понятий (операторы и скобки) в одном методе.

### Недостатки плана Qwen36

1. Удаление `.leftParenthesis` из `isOperatorOrLeftParen` меняет поведение метода во ВСЕХ четырёх местах его использования, а не только в проблемном кейсе nextIsOp для binaryOperator.
2. Некоторые выражения, которые сейчас ловятся на этапе токенизации (например `(+)`, `()`), после исправления будут проходить токенизацию и попадут в парсер с другой ошибкой (`invalidExpression` вместо `doubleOperator`). Это не критично, но меняет пользовательский опыт.
3. В разделе 2.1 описан сценарий с двумя закрывающими скобками `4*(2+3))`, что может вводить в заблуждение — баг проявляется и при одной закрывающей скобке `4*(2+3)`.

### Достоинства плана MiMoCode

1. Хирургическое, максимально точечное изменение: модифицируется ровно одна проверка (nextIsOp для binaryOperator).
2. Все остальные проверки (prevIsOp для всех кейсов, percent next-check, unaryMinus prevIsOp) остаются без изменений — ни одно существующее поведение не меняется.
3. Новый метод `isOperatorOnly` имеет понятное имя и русскоязычный комментарий, объясняющий его назначение.
4. Более безопасный подход: меньше риск непредвиденных побочных эффектов.

### Недостатки плана MiMoCode

1. Добавляет новый метод в код (хотя он приватный), что немного увеличивает размер файла.
2. Содержит неверные утверждения (см. раздел 3 ниже).

**Вставляемый код (7 строк):**

```swift
/// Проверяет, является ли токен оператором (без скобок).
/// Используется для проверки следующего токена после binaryOperator:
/// оператор после оператора — ошибка, но скобка после оператора — норма.
private func isOperatorOnly(_ token: Token) -> Bool {
    switch token {
    case .binaryOperator, .unaryMinus:
        return true
    default:
        return false
    }
}
```

**Пояснение:**
- Метод `private` — доступен только внутри структуры `Tokenizer`.
- Возвращает `true` ТОЛЬКО для `.binaryOperator` и `.unaryMinus`.
- НЕ возвращает `true` для `.leftParenthesis`, `.rightParenthesis`, `.percent`, `.number`.
- Комментарий на русском языке (согласно AGENTS.md, раздел 1).
- Идентификатор `isOperatorOnly` на английском языке (согласно AGENTS.md, раздел 8).

## ЧАСТЬ 7. РИСКИ И ИХ МИНИМИЗАЦИЯ

### Риск 1: Изменение сломает существующие тесты

**Вероятность:** крайне низкая  
**Опровержение:** Единственный юнит-тест на doubleOperator (`testTokenize_DoubleOperator`, строка 193) проверяет `"5++3"` — выражение без скобок. Тест `testTokenize_ComplexExpression` (строка 210) проверяет `"((15+16)*5)/3"` — умножение precedено `)` а не `(`, поэтому не затронуто. TestRunner содержит тесты на корректные выражения со скобками (`(15+16)*5`, строка 99), которые работают через парсер и не зависят от токенизации в части doubleOperator.

### Риск 2: Изменение повлияет на определение унарного минуса

**Вероятность:** нулевая  
**Опровержение:** Метод `lastTokenIsOperatorOrLeftParen` (строки 314-322), используемый для определения унарного/бинарного минуса (строка 67), НЕ ИЗМЕНЯЕТСЯ. Он по-прежнему включает `.leftParenthesis`, что корректно: `-` после `(` должен быть унарным.

### Риск 3: Изменение создаст новые невалидные выражения, проходящие токенизацию

**Вероятность:** низкая  
**Опровержение:** Единственное изменение — `nextIsOp` для кейса `.binaryOperator` перестанет считать `.leftParenthesis` оператором. Это означает, что комбинация «бинарный оператор + открывающая скобка» больше не будет ошибкой токенизации. Но это ИСПРАВЛЕНИЕ БАГА, а не новая регрессия. Все по-настоящему невалидные выражения (двойные операторы, `%` после `%`, унарный минус после унарного минуса и т.д.) продолжают ловиться другими кейсами валидации или парсером.

### Риск 4: Выражение `+(2+3)` перестанет валидироваться на этапе токенизации

**Вероятность:** N/A (это не регрессия)  
**Пояснение:** Выражение `+(2+3)` начинается с бинарного оператора `+`. В текущем коде оно ловится как doubleOperator (prevIsOp = false для первого токена, nextIsOp = isOperatorOrLeftParen(LP) = true → throw). После исправления: prevIsOp = false, nextIsOp = isOperatorOnly(LP) = false → проходит токенизацию. Но парсер не сможет построить валидный AST из `[binaryOperator(.add), leftParenthesis, ...]` — бинарному оператору не хватает левого операнда. Ошибка возникнет на этапе `buildAST` (строка 103 Parser.swift: `guard stack.count >= 2`). Это корректное поведение — выражение действительно невалидно, просто ошибка будет поймана на другом этапе с другим сообщением (`invalidExpression` вместо `doubleOperator`).

## ЧАСТЬ 8. ПОЧЕМУ ВЫБРАН ПОДХОД MiMoCode А НЕ Qwen36

Подход MiMoCode (создание нового метода `isOperatorOnly`) выбран как более безопасный по следующим причинам:

1. **Точечность:** Изменяется ровно одна строка кода (строка 331). Подход Qwen36 удаляет `.leftParenthesis` из общего метода, что влияет на все четыре места его использования в `validateTokenSequence`.

2. **Сохранение существующего поведения:** С подходом MiMoCode выражение `(+2)` по-прежнему будет ловиться как doubleOperator (через prevIsOp проверку в кейсе binaryOperator), потому что prevIsOp по-прежнему использует `isOperatorOrLeftParen` с `.leftParenthesis`. Подход Qwen36 изменил бы это поведение.

3. **Предсказуемость:** При ревью кода легче понять, зачем нужен метод `isOperatorOnly` (он используется только в одном месте для конкретной цели), чем почему из общего метода убрана скобка, которая может быть нужна в других контекстах.

4. **Минимальный риск регрессии:** Поскольку изменяется ровно одна проверка, вероятность непредвиденных побочных эффектов стремится к нулю.
