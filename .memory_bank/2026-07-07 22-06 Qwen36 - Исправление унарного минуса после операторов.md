## 1. Описание проблемы

## 2. Глубокий анализ корневой причины

### 2.1. Цепочка вызовов при клавиатурном вводе "5*-3"

**Шаг 1: Ввод '5'**
- `KeyHandlerNSView.keyDown(with:)` → `CalculatorApp.swift:96-100`, default case
- Вызов: `viewModel.appendCharacter("5")` → `CalculatorViewModel.swift:60-78`
- Результат: `expression = "5"`, автовычисление → `result = "5"`, `resultDecimal = 5`

**Шаг 2: Ввод '*' (Numpad *, keyCode 67)**
- `CalculatorApp.swift:86`: `viewModel.appendCharacter("*")`
- `hasResult == true`, `isOperator("*") == true` → ветка `CalculatorViewModel.swift:67-73`
- `expression = "5"` (dec.description от resultDecimal=5)
- `result = nil`, `resultDecimal = nil`
- `appendCharacter`: `expression += "*"` → `"5*"`
- `isDigitOrDecimal("*") == false` → вызов `tryAutoEvaluate()`

**Шаг 3: Автовычисление "5*" (CalculatorViewModel.swift:244-255)**
- `trimmed = "5*"`, не пустой ✓
- `isTrailingOperator("5*")`: last char = "*", return true → `CalculatorViewModel.swift:257-260`
- Условие `!isTrailingOperator(expression)` == false → **ранний выход**
- Ошибки нет, выражение `"5*"` отображается

**Шаг 4: Ввод '-' (Numpad −, keyCode 78)**
- `CalculatorApp.swift:88`: `viewModel.appendCharacter("-")`
- `hasResult == false` → пропускаем ветку результата
- `expression += "-"` → `"5*-"`
- `isDigitOrDecimal("-") == false` → вызов `tryAutoEvaluate()`

**Шаг 5: Автовычисление "5*-" — ЗДЕСЬ ПРОИСХОДИТ ОШИБКА**

Вызов: `engine.evaluate("5*-")` → `CalculatorEngine.swift:23-41`

```
preprocess("5*-") → "5*-" (без изменений)
Tokenizer.tokenize("5*-"):
  '5' → number(5)
  '*' → binaryOperator(.multiply)
  '-' → tokens.last = .binaryOperator(.multiply), lastTokenIsOperatorOrLeftParen = true → unaryMinus
  validateTokenSequence([number(5), binaryOperator(.multiply), unaryMinus]):
    - binaryOperator(.multiply): prevIsOp=false, nextIsUnaryMinus=true → OK ✓
    - unaryMinus: prevIsBinaryOp=true → условие "prevIsOp && !prevIsBinaryOp" = false → OK ✓
  tokens = [number(5), binaryOperator(.multiply), unaryMinus] ✓

Parser.parse([number(5), binaryOperator(.multiply), unaryMinus]):
  toRPN(tokens):
    number(5) → output: [5]
    binaryOperator(.multiply): stack пуст → push * → stack: [*]
    unaryMinus: top=*, precedenceValue(*) = 2, precedenceValue(unaryMinus) = 2
      Условие: "top.precedenceValue > token.precedenceValue" → 2 > 2 = false ✗
      Условие: "(top.precedenceValue == token.precedenceValue && top.isLeftAssoc)" → (2==2 && true) = true ✓
      → pop * to output, push unaryMinus
      output: [5, *], stack: [unaryMinus]
  RPN = [5, *, unaryMinus]

buildAST(from: [5, *, unaryMinus]):
    number(5) → stack: [.number(5)]
    binaryOperator(.multiply): pop right=.number(5), pop left... STACK EMPTY!
      → throw CalculatorError.invalidExpression("Invalid expression") ← ОШИБКА!
```

**Корневая причина:** `precedenceValue` для `unaryMinus` равен 2 (такой же как у `*`). В алгоритме Shunting Yard это заставляет `*` выталкиваться в выходной буфер **до** помещения `unaryMinus` в стек операторов. Результат — RPN `[5, *, -]`, который невалиден для построения AST (бинарный оператор `*` получает только один операнд).

### 2.2. Верификация корневой причины

Файл: `Sources/CalculatorEngine/Parser/Precedence.swift:26-37`
```swift
var precedenceValue: Int {
    switch self {
    case .binaryOperator(let op):
        return op.precedence.rawValue   // multiply/divide = 2 ✓
    case .percent:
        return 2                          // На уровне × и ÷
    case .unaryMinus:
        return 2   // На уровне × и ÷     ← ПРОБЛЕМА! Должно быть > 2
    default:
        return 1   // На уровне + и −
    }
}
```

Файл: `Sources/CalculatorEngine/Parser/Precedence.swift:39-48`
```swift
var isLeftAssoc: Bool {
    switch self {
    case .binaryOperator, .percent:
        return true
    case .unaryMinus:
        return false  // unary minus — right-associative (важно для "5*-3" = 5*(-3))
    default:
        return false
    }
}
```

**Комментарий в коде (`Precedence.swift:44`) утверждает**, что `unaryMinus` имеет правую ассоциативность и важен для `"5*-3" = 5*(-3)`. Однако **правая ассоциативность не помогает**, потому что условие выталкивания в `Parser.swift:46-47`:

```swift
if top.precedenceValue > token.precedenceValue ||
   (top.precedenceValue == token.precedenceValue && top.isLeftAssoc) {
    output.append(operatorStack.removeLast())  // * выталкивается из-за isLeftAssoc=true
} else {
    break  // unaryMinus не должен здесь оказываться в output
}
```

Поскольку `precedenceValue(unaryMinus) == precedenceValue(multiply) == 2` и `isLeftAssoc(*) == true`, условие срабатывает и `*` выталкивается. Это **архитектурная ошибка**: правая ассоциативность унарного минуса не имеет смысла, если его приоритет равен приоритету бинарных операторов умножения/деления.

### 2.3. Почему "5*(-3)" даёт "doubleOperator"

Файл: `Sources/CalculatorEngine/Tokenizer/Tokenizer.swift:346-355`
```swift
case .unaryMinus:
    let prevIsOp = i > tokens.startIndex && isOperatorOrLeftParen(tokens[i - 1])
    let prevIsBinaryOp: Bool = {
        guard i > tokens.startIndex else { return false }
        if case .binaryOperator(_) = tokens[i - 1] { return true }
        return false
    }()
    if prevIsOp && !prevIsBinaryOp {
        throw CalculatorError.doubleOperator
    }
```

Для `"5*(-3)"`:
- Токены: `[number(5), binaryOperator(.multiply), leftParenthesis, unaryMinus, number(3)]`
- При обработке `unaryMinus` (индекс 3): `tokens[2] = .leftParenthesis`
- `prevIsOp = true` (leftParenthesis) ✓
- `prevIsBinaryOp = false` (leftParenthesis — не binaryOperator) ✓
- Условие: `true && !false = true` → **throw doubleOperator** ← ОШИБКА!

**Вторая корневая причина:** Валидация последовательности токенов (`validateTokenSequence`) ошибочно считает комбинацию `(` + `unaryMinus` как "двойной оператор". Однако `(-3)` — абсолютно валидная математическая запись. Условие должно разрешать `unaryMinus` после открывающей скобки.

### 2.4. Почему Cmd+V даёт "clipboard.cannotEvaluate"

Файл: `Sources/ViewModels/CalculatorViewModel.swift:207-222`
```swift
func insertFromClipboard(_ text: String) {
    let trimmed = text.trimmingCharacters(in: .whitespacesAndNewlines)
    guard !trimmed.isEmpty else { return }

    clear()

    if let value = try? engine.evaluate(trimmed) {  // ← try? ПОДАВЛЯЕТ ошибку!
        expression = trimmed
        result = formatter.format(value)
        resultDecimal = value
        historyService.add(expression: trimmed, result: value)
    } else {
        errorMessage = NSLocalizedString("clipboard.cannotEvaluate", comment: "")
    }
}
```

`try? engine.evaluate("5*-3")` подавляет ошибку `CalculatorError.invalidExpression`. Условие `if let value` == false → показывается `"clipboard.cannotEvaluate"`. Это **не баг**, а следствие первой корневой причины — если движок правильно обрабатывает унарный минус, вставка тоже заработает.

## 3. Архитектурное решение

### 3.1. Что исправляем

**Исправление 1: Приоритет унарного минуса (Precedence.swift)**
- Изменить `precedenceValue` для `.unaryMinus` с `2` на `3`
- Это обеспечит, что унарный минус имеет **более высокий приоритет**, чем бинарные операторы умножения/деления
- В алгоритме Shunting Yard это предотвратит преждевременное выталкивание `*` в выходной буфер

**Исправление 2: Валидация последовательности токенов (Tokenizer.swift)**
- Изменить условие для `.unaryMinus` в `validateTokenSequence`, чтобы разрешить `unaryMinus` после `.leftParenthesis`
- Текущее условие бросает `doubleOperator` для `(-3)`, что неверно

**Исправление 3: Автовычисление при неполных выражениях (CalculatorViewModel.swift)**
- Добавить проверку `errorMessage != nil` в условие раннего выхода `tryAutoEvaluate()`
- Если уже есть ошибка, не перезаписывать `result`/`resultDecimal` попыткой автовычисления неполного выражения

### 3.2. Почему это решение архитектурно верно

1. **Минимальное вмешательство:** Изменяются только два файла вычислительного движка (Precedence.swift, Tokenizer.swift) и один файл ViewModel
2. **Соответствие математике:** Унарный минус действительно имеет более высокий приоритет, чем бинарные операторы умножения/деления: `5*-3 = 5*(-3)`, а не `(5*)*(-3)`
3. **Нет регрессий:** Приоритет унарного минуса (3) выше приоритета сложения/вычитания (1), что корректно для всех существующих сценариев
4. **Согласованность с документацией:** Comment в `Precedence.swift:44` говорит "важно для 5*-3 = 5*(-3)" — исправление делает код соответствующим документации

### Шаг 1: Исправление приоритета унарного минуса

**Файл:** `Sources/CalculatorEngine/Parser/Precedence.swift`  
**Строка:** 32-33

**Текущий код:**
```swift

```

**Новый код:**
```swift
    case .unaryMinus:
        return 3   // Выше, чем у × и ÷ — чтобы "5*-3" парсилось как "5*(-3)"
```

**Обоснование:**
- `Precedence.unaryMinus.rawValue = 3` (файл `Precedence.swift:6`)
- Текущий код игнорирует это значение и хардкодит `2`
- Значение `3` означает, что унарный минус имеет более высокий приоритет, чем бинарные операторы умножения/деления (`rawValue = 2`)
- Это корректно с математической точки зрения: `5*-3 = 5*(-3)`, а не `(5*)*(-3)`

**Проверка влияния на другие выражения:**

| Выражение | Старый RPN | Новый RPN | Результат |
|---|---|---|---|
| `-5+12` | `[−, 5, +, 12]` → `add(unaryMinus(5), 12)` = 7 | `[−, 5, +, 12]` → то же = 7 | ✅ Без изменений |
| `--5` | `[−, −, 5]` → `unaryMinus(unaryMinus(5))` = 5 | `[−, −, 5]` → то же = 5 | ✅ Без изменений |
| `5*-3` | `[5, *, −]` → **ошибка** (нехватка операндов) | `[5, −, 3, *]` → `multiply(unaryMinus(3), 5)` = -15 | ✅ Исправлено |
| `5/-3` | `[5, /, −]` → **ошибка** | `[5, −, 3, /]` → `divide(unaryMinus(3), 5)` = -1.667 | ✅ Исправлено |
| `-2*3` | `[−, 2, *, 3]` → `multiply(unaryMinus(2), 3)` = -6 | `[−, 2, *, 3]` → то же = -6 | ✅ Без изменений |
| `10%-5` | `%` идёт в output сразу (не сравнивается с unaryMinus) | То же | ✅ Без изменений |

**Верификация через алгоритм Shunting Yard для "5*-3" после исправления:**

```
tokens: [number(5), binaryOperator(.multiply), unaryMinus, number(3)]

output: [], stack: []

1. number(5) → output
   output: [5], stack: []

2. binaryOperator(.multiply):
   stack пуст → push *
   output: [5], stack: [*]

3. unaryMinus (precedenceValue = 3):
   top = *, precedenceValue(*) = 2
   Условие выталкивания: "top.precedenceValue > token.precedenceValue"
     → 2 > 3 = false ✗

4. number(3) → output
   output: [5, 3], stack: [*, unaryMinus]

Конец токенов. Остаток стека (pop all):
   pop unaryMinus → output: [5, 3, unaryMinus]
   pop *          → output: [5, 3, unaryMinus, *]
```

### Шаг 2: Исправление валидации последовательности токенов для унарного минуса после скобки

**Файл:** `Sources/CalculatorEngine/Tokenizer/Tokenizer.swift`  
**Строка:** 346-355

**Текущий код:**
```swift
            case .unaryMinus:
                let prevIsOp = i > tokens.startIndex && isOperatorOrLeftParen(tokens[i - 1])
                let prevIsBinaryOp: Bool = {
                    guard i > tokens.startIndex else { return false }
                    if case .binaryOperator(_) = tokens[i - 1] { return true }
                    return false
                }()
                if prevIsOp && !prevIsBinaryOp {
                    throw CalculatorError.doubleOperator
                }
```

**Проблема:** `isOperatorOrLeftParen` (строка 369-376) возвращает `true` для `.leftParenthesis`. Условие `prevIsOp && !prevIsBinaryOp` срабатывает для `(-3)`, потому что:
- `tokens[i-1] = .leftParenthesis` → `isOperatorOrLeftParen` = true → `prevIsOp = true`
- `tokens[i-1] != .binaryOperator(_)` → `prevIsBinaryOp = false`
- Итог: `true && !false = true` → ошибка

**Новый код:**
```swift
            case .unaryMinus:
                let prevToken = i > tokens.startIndex ? tokens[i - 1] : nil
                switch prevToken {
                case .binaryOperator, .unaryMinus:
                    throw CalculatorError.doubleOperator
                default:
                    break
                }
```

**Обоснование:**
- Унарный минус — ошибка только если предыдущий токен является бинарным оператором (`+`, `-`, `*`, `/`) или другим унарным минусом (кроме случаев вроде `--5`, которые токенизатор корректно обрабатывает как два отдельных минуса)
- `leftParenthesis` после которого идёт `unaryMinus` — абсолютно валидная конструкция: `(-3)`, `(5+-3)` и т.д.
- Упрощение кода: вместо двух переменных (`prevIsOp`, `prevIsBinaryOp`) и сложного условия — прямой switch по предыдущему токену

**Проверка для "5*(-3)":**
```
tokens: [number(5), binaryOperator(.multiply), leftParenthesis, unaryMinus, number(3)]

i=0: number(5) → default → break ✓
i=1: binaryOperator(.multiply):
     prevIsOp=false (i=startIndex)
     nextIsUnaryMinus=true → условие "nextIsOp && !nextIsUnaryMinus" = false → OK ✓
i=2: leftParenthesis → default → break ✓
i=3: unaryMinus:
     prevToken = tokens[2] = .leftParenthesis
     switch .leftParenthesis → default → break ✅ (НЕ бросает ошибку!)
i=4: number(3) → default → break ✓

validateTokenSequence завершается без ошибок ✅
```

**Проверка для "5++3" (должна оставаться ошибкой):**
```
tokens: [number(5), binaryOperator(.add), binaryOperator(.add), number(3)]

i=2: binaryOperator(.add):
     prevIsOp = true (tokens[1] = .binaryOperator(.add))
     → throw CalculatorError.doubleOperator ✅
```

**Проверка для "%*5" (должна оставаться ошибкой):**
```
tokens: [percent, binaryOperator(.multiply), number(5)]

i=0: percent:
     prevIsOp=false (i=startIndex) ✓
     nextIsOp=true (tokens[1] = .binaryOperator(.multiply)) → throw doubleOperator ✅
```

### Шаг 3: Защита автовычисления от перезаписи результата при ошибке

**Файл:** `Sources/ViewModels/CalculatorViewModel.swift`  
**Строка:** 244-255

**Текущий код:**
```swift
    private func tryAutoEvaluate() {
        let trimmed = expression.trimmingCharacters(in: .whitespaces)
        guard !trimmed.isEmpty, !isTrailingOperator(expression), !hasUnclosedParentheses(trimmed) else { return }

        do {
            let value = try engine.evaluate(expression)
            result = formatter.format(value)
            resultDecimal = value
        } catch {
            errorMessage = error.localizedDescription
        }
    }
```

**Проблема:** При вводе `"5*-"` автовычисление бросает `invalidExpression`, устанавливает `errorMessage`. Пользователь видит ошибку, но она может быть запутывающей — выражение ещё не завершено. После исправлений Шагов 1 и 2 эта конкретная ошибка больше не возникнет для валидных выражений, но защита от перезаписи результата при ошибке автовычисления остаётся полезной.

**Новый код:**
```swift
    private func tryAutoEvaluate() {
        let trimmed = expression.trimmingCharacters(in: .whitespaces)
        guard !trimmed.isEmpty, !isTrailingOperator(expression), !hasUnclosedParentheses(trimmed) else { return }

        do {
            let value = try engine.evaluate(expression)
            result = formatter.format(value)
            resultDecimal = value
        } catch {
            // Если уже есть ошибка — не перезаписываем errorMessage новым сообщением
            // от неполного выражения (например, "5*-" при вводе "*" затем "-")
            if errorMessage == nil {
                errorMessage = error.localizedDescription
            }
        }
    }
```

**Обоснование:**
- Если пользователь вводит `"5*-3"` по символам, после ввода `'-'` выражение `"5*-"` невалидно (нехватка операнда для унарного минуса)
- До исправлений Шага 1 это вызывало ошибку `invalidExpression`, которая показывалась пользователю на мгновение до ввода следующего символа (следующий символ вызывает `clearError()`)
- После исправлений Шага 1 выражение `"5*-"` всё ещё невалидно (нет операнда после унарного минуса), но ошибка теперь будет подавлена, если уже была установлена другая ошибка
- Это предотвращает "мигание" разных сообщений об ошибке при быстром вводе
