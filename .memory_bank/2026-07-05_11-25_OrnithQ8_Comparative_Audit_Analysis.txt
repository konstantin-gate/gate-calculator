## 1. Общая характеристика подходов

### UnslothMTP — «Инженерный аудит с матрицей соответствия»

**Стиль:** Структурированный технический отчёт с нумерованными категориями (C-01..N-09), матрицей соответствия SRS по секциям, детальным анализом граничных случаев.

**Сильные стороны:**
- Наиболее полная матрица соответствия SRS (48 строк, охват всех 96 секций)
- Детальный раздел «неучтённые нюансы реализации» (8.1–8.10) с пошаговым трассированием кода
- Подсчёт метрик: 4 критических, 7 серьёзных, 11 средней тяжести, 9 незначительных, 20+ положительных находок
- Положительные находки (P-01..P-20) — уникальный раздел, которого нет у других аудиторов
- Оценка соответствия по категориям с процентами (архитектура 95%, Engine 95%, UI/UX 65% и т.д.)

**Слабые стороны:**
- Не обнаружил критическую проблему с тестами в Package.swift (отсутствие testTarget)
- Не проверил корректность условия `char.lowercased() == "pi"` в Tokenizer
- Не заметил ошибку Parser (extraClosingParenthesis вместо missingClosingParenthesis)
- Не выявил проблему с вставкой из буфера (#V-01 у Sonnet)
- Не обнаружил дублирование NumberFormatter в Decimal+Extensions.swift vs NumberFormatterService

### Sonnet — «Детективный аудит с фокусом на баги»

**Стиль:** Аудит-расследование, сфокусированный на обнаружении конкретных багов и логических ошибок. Нумерация по категориям (A-01..T-05, E-01..E-06, V-01..V-06, UI-01..UI-10, S-01..S-05, ACC-01..ACC-03, K-01, ST-01..ST-02).

**Сильные стороны:**
- Обнаружил **самую критичную проблему**: тесты не зарегистрированы в Package.swift (#A-03, #T-01) — это блокирует `swift test`
- Единственный аудитор, обнаруживший логическую ошибку `char.lowercased() == "pi"` (#E-01) — сравнение Character с String «pi» невозможно
- Единственный, кто нашёл неверный тип ошибки в Parser (#E-03): extraClosingParenthesis вместо missingClosingParenthesis
- Обнаружил проблему с вставкой из буфера (#V-01): выражение очищается, пользователь не видит что вставил
- Выявил проблему с экспоненциальным форматированием (#S-02): NumberFormatter выдаёт «E», а код ищет «e»
- Нашёл проблему с toggleSign/memoryAdd (#V-04, #V-05): Decimal(string:) не парсит числа с разделителями тысяч
- Обнаружил дублирование NumberFormatter в Decimal+Extensions.swift (#S-04)
- Указал на проблему с `isMathExpression` — мёртвый код в двух местах (#S-05)
- Нашёл проблему с шириной кнопки «0» — захардкоженный +12 (#UI-05)
- Обнаружил прямое обращение HistoryPanelView к HistoryService вместо ViewModel (#UI-07)
- Указал на отсутствие @MainActor у KeyHandlerNSView (#UI-10)
- Обнаружил проблему с форматированием выражения: точки заменяются безусловно (#UI-03), унарный/бинарный минус не различаются (#UI-04)
- Нашёл TODO в production-коде (#UI-02)

**Слабые стороны:**
- Не дал положительных находок (нет раздела «что сделано хорошо»)
- Не привёл общую оценку соответствия в процентах
- Не провёл анализ граничных случаев (edge cases)
- Некоторые утверждения требуют уточнения (см. раздел 3 ниже)

### OrnithQ8 — «Стратегический аудит с приоритизацией»

**Стиль:** Executive Summary + структурированные разделы по темам. Нумерация по секциям SRS (1.1..3.6, 4.1..5.3, 6.1..8.1, 9.1). Приоритетная таблица P0-P3.

**Сильные стороны:**
- Лучшая структура для руководства: Executive Summary в начале, приоритеты P0-P3 в конце
- Дает обоснования для некоторых архитектурных решений (singleton HistoryService, @unchecked Sendable)
- Упоминает Dynamic Type как нерализованную функцию (SRS Section 64, 83) — уникальная находка
- Упоминает benchmark tests для критических путей (SRS Section 86) — уникальная рекомендация
- Оценка соответствия по категориям с процентами (аналогично UnslothMTP)
- Лаконичность — самый короткий отчёт, но покрывает ключевые проблемы

**Слабые стороны:**
- Самый поверхностный из трёх — наименьшее количество выявленных проблем (~25 vs 44 у Sonnet)
- Не обнаружил критические баги в Tokenizer (pi, e3, бесконечные циклы)
- Не нашёл проблему с тестами в Package.swift
- Не обнаружил ошибку Parser (extraClosingParenthesis)
- Не выявил проблему с вставкой из буфера
- Не нашёл дублирование NumberFormatter
- Не указал на проблему с экспоненциальным форматированием
- Раздел «Архитектурные замечания» содержит слабые обоснования (singleton оправдан, но SRS §18 прямо запрещает)
- Не проверил фактическое использование Decimal+Extensions.swift

## 3. Выявленные неучтённые ни одним из аудиторов нюансы

### 3.1. CalculatorEngineTests: сравнение через .description (#T-04 у Sonnet — верное замечание)

Sonnet верно указал на нестабильное сравнение `XCTAssertEqual(result.description, expected.description)`. Decimal.description может варьировать формат в зависимости от внутренних представлений. Рекомендуется использовать `XCTAssertEqual(result, expected)` напрямую.

### 3.2. Precedence: percent vs unaryMinus — семантическая проблема (UnslothMTP M-07)

Precedence.swift:6-7 устанавливает `unaryMinus = 3`, `percent = 4`. Это означает, что percent обрабатывается ПОСЛЕ unaryMinus в toRPN.

Для выражения `-5%`:
- Tokenizer: [.unaryMinus, .number(5), .percent]
- toRPN: unaryMinus push → 5 в output → percent: pop operators с precedence > 4. unaryMinus имеет 3 < 4, не pop'ится. Output: [5, percent], stack: [unaryMinus]
- buildAST: 5/100 = 0.05 → unaryMinus(0.05) = -0.05

Результат верный (-0.05), но семантика: `-(5%)` вместо `(-5)%`. Для калькулятора это не критично, но SRS Section 28 говорит что унарный минус и %, /, * должны быть на одном уровне.

### 3.3. ClipboardManager: нет потокобезопасности для NSPasteboard

ClipboardManager.swift не использует никаких блокировок при обращении к NSPasteboard. В отличие от HistoryService (NSLock) и CalculatorViewModel (@MainActor), ClipboardManager может быть вызван из любого контекста. NSPasteboard не является потокобезопасным без синхронизации.

### 3.4. CalculatorViewModel: formatter.format(dec) записывает локализованную строку обратно в expression

CalculatorViewModel.swift:32, 46:
```swift
expression = formatter.format(dec)
```

`formatter` — это NumberFormatterService.shared, который использует Locale.current. Для русской локали `format(Decimal(string:"1.5")!)` вернёт `"1,5"`. Затем `engine.evaluate("1,5")` — Tokenizer preprocess не конвертирует запятую в точку (см. 3.2), и readNumber вернёт (0, start) → бесконечный цикл.

Это **скрытый критический баг**, который ни один из трёх аудиторов не обнаружил.

### 3.5. KeyHandlerNSView: клавиша "," обрабатывается, но конвертируется в "."

CalculatorApp.swift:78:
```swift
let normalized = char == "," ? "." : String(char)
viewModel.appendCharacter(normalized)
```

Это корректная обработка — запятая с клавиатуры конвертируется в точку. Однако это противоречит SRS Section 31, который говорит «желательно учитывать локаль». Если пользователь вводит «1,5» с клавиатуры — будет «1.5». Но если он вставляет «1,5» из буфера (⌘V) — см. 3.4 выше.

### 3.6. CalculatorButton: .cornerRadius(diameter / 2) делает кнопки круглыми

CalculatorView.swift использует `clipShape(Circle())` или `.cornerRadius(diameter / 2)`. SRS Section 42 требует радиус 12pt. Кнопки должны быть скруглёнными квадратами (cornerRadius: 12), а не идеальными кругами. Это верно для стандартного режима (где diameter = 66pt, radius = 33pt ≠ 12pt).

### 3.7. Package.swift: Extensions и Components отсутствуют в sources CalculatorApp

Package.swift:32-42 перечисляет: App, Views, ViewModels, Services, History, Clipboard, Models, Formatting, Theme.

Отсутствуют:
- `Components` — EmptyStateView.swift не компилируется в CalculatorApp
- `Extensions` — Decimal+Extensions.swift и String+Calculator.swift не компилируются в CalculatorApp

Это означает, что даже если бы эти файлы использовались, они не попали бы в бинарь. К счастью, Decimal+Extensions действительно не используется (подтверждено), а String+Calculator.swift тоже не вызывается напрямую. Но это архитектурная ошибка в Package.swift.

## 7. Общие выводы

### 7.1. Какой аудитор лучше всего справился?

**Sonnet** — безусловный лидер по полноте и точности обнаружения проблем. Он нашёл 44 проблемы, включая самые критичные: неработающие тесты, баги в ядре (Tokenizer, Parser), UX-проблемы (вставка из буфера). Его аудит наиболее полезен для практического исправления проекта.

**UnslothMTP** — второй по полноте (29 проблем), с лучшей глубиной анализа граничных случаев и уникальными положительными находками. Однако пропустил несколько критических багов в ядре.

**OrnithQ8** — самый поверхностный (25 проблем), но с лучшей структурой для руководства (Executive Summary, приоритеты P0-P3). Полезен как обзор, но недостаточен для принятия технических решений.

### 7.2. Что не обнаружил ни один аудитор?

1. **Скрытый критический баг:** `CalculatorViewModel` записывает результат `formatter.format(dec)` (локализованную строку, например "1,5") обратно в `expression`. При последующей оценке `engine.evaluate("1,5")` Tokenizer не конвертирует запятую → readNumber возвращает (0, start) → бесконечный цикл. Это происходит при нажатии оператора после результата в русской локали.

2. **ClipboardManager без синхронизации:** В отличие от HistoryService (NSLock), ClipboardManager не использует блокировок при обращении к NSPasteboard.

3. **Кнопки — идеальные круги вместо скруглённых квадратов:** SRS требует cornerRadius 12pt, но используется Circle() / diameter/2.

### 7.3. Рекомендация

Для полного аудита проекта следует объединить сильные стороны всех трёх отчётов:
- Критические баги Sonnet (Tokenizer, Parser, Package.swift, ViewModel)
- Глубину анализа UnslothMTP (граничные случаи, положительные находки, матрица SRS)
- Структуру и приоритизацию OrnithQ8 (Executive Summary, P0-P3)
