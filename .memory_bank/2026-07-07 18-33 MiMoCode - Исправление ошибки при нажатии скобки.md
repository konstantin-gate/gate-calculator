# План исправления: ошибка `missingClosingParenthesis` при нажатии кнопки «(»

**Дата:** 2026-07-07  
**Агент:** MiMoCode  
**Статус:** План готов к исполнению  
**Затронутые слои:** ViewModel (1 файл, 1 метод, 1 новый приватный метод)

---

## 1. Описание проблемы

При нажатии кнопки «(» на клавиатуре калькулятора на дисплее появляется ошибка `errors.missingParenthesis` («Пропущена закрывающая скобка»).

Ожидаемое поведение: символ «(» добавляется в expression без ошибок, калькулятор показывает «(» на дисплее.

**Ключевой сценарий:** `(15 + 16 + 17 + 18)/4 =` — калькулятор должен позволять вводить скобки.

---

## 2. Корневая причина (Root Cause Analysis)

### 2.1. Полная цепочка вызовов при нажатии «(»

| Шаг | Файл | Строка | Действие |
|---|---|---|---|
| 1 | `CalculatorView.swift` | `handleButtonPress` | `viewModel.appendCharacter("(")` |
| 2 | `CalculatorViewModel.swift` | `:60-79` | `expression += "("` → `isDigitOrDecimal("(")` = `false` → вызов `tryAutoEvaluate()` |
| 3 | `CalculatorViewModel.swift` | `:244-255` | `engine.evaluate("(")` |
| 4 | `CalculatorEngine.swift` | `:23-41` | `Tokenizer.tokenize("(")` → `[.leftParenthesis]` |
| 5 | `Parser.swift` | `:20-92` | `toRPN([.leftParenthesis])` → остаток стека = `[.leftParenthesis]` → **строка 83:** `throw CalculatorError.missingClosingParenthesis` |
| 6 | `CalculatorViewModel.swift` | `:252-254` | `errorMessage = error.localizedDescription` → отображение на дисплее |

### 2.2. Суть дефекта

Метод `tryAutoEvaluate()` (CalculatorViewModel.swift:244-255) пытается вычислить выражение после каждого ввода символа, не являющегося цифрой или десятичным разделителем. Скобки — не операторы (`isOperator("(")` возвращает `false`), поэтому `tryAutoEvaluate()` вызывается. Выражение «(» является неполным (незакрытая скобка), и вычислительный движок корректно выбрасывает ошибку `missingClosingParenthesis`.

**Ошибка НЕ в вычислительном движке** — движок правильно определяет, что выражение невалидно. Ошибка в ViewModel, который пытается вычислить промежуточное, заведомо неполное выражение.

## 3. Решение

### 3.1. Архитектурное обоснование

Единственное верное место исправления — **ViewModel** (CalculatorViewModel.swift), так как:

1. **Движок (CalculatorEngine) не должен изменяться** — он корректно определяет невалидные выражения. Семантика «(» без «)» — действительно ошибка для вычисления.
2. **View-слой не должен изменяться** — кнопка уже корректно вызывает `appendCharacter("(")`.
3. **ViewModel отвечает за решение «попытаться вычислить или нет»** — это его область ответственности в MVVM.

### 3.2. Метод исправления

Добавить проверку сбалансированности скобок в метод `tryAutoEvaluate()`. Если в expression количество открывающих скобок больше закрывающих — не пытаться вычислять, а молча пропустить автовычисление.

Почему именно проверка `openCount > closeCount` (а не `openCount != closeCount`):
- При вводе `(` : openCount=1, closeCount=0 → `openCount > closeCount` = `true` → пропуск
- При вводе `(15+16)` : openCount=1, closeCount=1 → `openCount > closeCount` = `false` → вычисление
- При вводе `((15+16)*5)` : openCount=2, closeCount=2 → `openCount > closeCount` = `false` → вычисление
- При вводе `((15+16` : openCount=2, closeCount=0 → `openCount > closeCount` = `true` → пропуск

Условие `openCount != closeCount` тоже корректно, но избыточно: если `openCount < closeCount`, это ошибка `extraClosingParenthesis`, и `tryAutoEvaluate` всё равно бросит ошибку. Но `openCount > closeCount` — минимально достаточное и семантически точное условие.

## 4. Пошаговый план реализации

### Шаг 1. Добавить приватный метод `areParenthesesBalanced`

**Файл:** `Sources/ViewModels/CalculatorViewModel.swift`  
**Расположение:** Блок `// MARK: - Private helpers` (строка 242), перед методом `tryAutoEvaluate` (строка 244)

**Добавить новый метод:**

```swift
/// Проверяет, что все открывающие скобки в expression закрыты.
/// Используется для предотвращения автовычисления при незакрытых скобках.
private func areParenthesesBalanced(_ expr: String) -> Bool {
    var openCount = 0
    for char in expr {
        if char == "(" { openCount += 1 }
        else if char == ")" { openCount -= 1 }
    }
    return openCount == 0
}
```

**Верификация:**
- Метод `areParenthesesBalanced` нигде не определён в проекте (подтверждено через `grep`) — конфликтов имён нет
- Метод приватный (`private`), не нарушает `Sendable`-контракт (класс `@MainActor`)
- Метод не требует импортов — использует только стандартные `String` и `Character`
- Сигнатура: `(String) -> Bool` — совместима с вызовом из `tryAutoEvaluate`

### Шаг 2. Добавить проверку в `tryAutoEvaluate`

**Файл:** `Sources/ViewModels/CalculatorViewModel.swift`  
**Строка:** 246 (внутри `tryAutoEvaluate`)

**Текущий код (строки 244-255):**
```swift
private func tryAutoEvaluate() {
    let trimmed = expression.trimmingCharacters(in: .whitespaces)
    guard !trimmed.isEmpty, !isTrailingOperator(expression) else {   // строка 246
        return
    }
    do {
        let value = try engine.evaluate(expression)
        result = formatter.format(value)
        resultDecimal = value

        errorMessage = error.localizedDescription
    }

```

**Новый код:**
```swift
private func tryAutoEvaluate() {
    let trimmed = expression.trimmingCharacters(in: .whitespaces)
    guard !trimmed.isEmpty,
          !isTrailingOperator(expression),
          areParenthesesBalanced(trimmed) else {                    // ДОБАВЛЕНО
        return
    }
    do {
        let value = try engine.evaluate(expression)
        result = formatter.format(value)
        resultDecimal = value
    } catch {
        errorMessage = error.localizedDescription
    }
}
```

**Изменение:** Одна строка добавлена в `guard`-условие на строке 246: `, areParenthesesBalanced(trimmed)`.

### Шаг 3. Верификация отсутствия побочных эффектов

#### 3.1. Все вызовы `tryAutoEvaluate()`

| Вызывающий метод | Строка | Сценарий | Влияние |
|---|---|---|---|
| `appendCharacter` | `:77` | Ввод не-цифры (оператор, скобка, константа) | **Улучшение:** скобки больше не вызывают ошибку |
| `backspace` | `:135` | Удаление символа | **Нет побочных эффектов:** если удалили «)», баланс может нарушиться → пропуск автовычисления → корректно |
| `useHistoryEntry` | `:234` | Выбор записи из истории | **Нет побочных эффектов:** записи истории содержат завершённые выражения (созданы через `evaluate()`) |

#### 3.2. Анализ сценариев

| Сценарий | expression | `areParenthesesBalanced` | Результат |
|---|---|---|---|
| Нажатие «(» | `"("` | `false` | Автовычисление пропущено → ошибка НЕ показывается ✅ |
| Нажатие «(» после «15+» | `"15+("` | `false` | Автовычисление пропущено ✅ |
| Нажатие «)» после «(15+16» | `"(15+16)"` | `true` | Автовычисление выполняется → `31` ✅ |
| Нажатие оператора после «(» | `"(+ "` | `false` | Автовычисление пропущено (guard) ✅ |
| Ввод `(15+16+17+18)/4` | `"(15+16+17+18)/4"` | `true` | Автовычисление выполняется → `16.5` ✅ |
| Ввод `((15+16)*5)/3` | `((15+16)*5)/3` | `true` | Автовычисление выполняется → `51.666...` ✅ |
| Нажатие «=» после «(15+16» | `"(15+16"` | `false` | `evaluate()` вызывается **напрямую** (не через tryAutoEvaluate) → ошибка `missingClosingParenthesis` показывается ✅ |
| Backspace при `(15+16)` | `"(15+16"` | `false` | Автовычисление пропущено → предыдущий результат сохраняется или сбрасывается — корректно ✅ |

#### 3.3. Важное замечание: `evaluate()` (нажатие «=») НЕ затронуто

Метод `evaluate()` (строки 97-116) вызывается **напрямую** по нажатию «=» и **не использует** `tryAutoEvaluate()`. Проверка сбалансированности скобок НЕ влияет на поведение при нажатии «=». Если пользователь введёт `(15+16` и нажмёт «=», ошибка `missingClosingParenthesis` по-прежнему будет показана — это корректное поведение.

## 5. Анализ альтернативных решений (и почему они отвергнуты)

### Альтернатива A: Изменить Tokenizer/Parser — «не бросать ошибку при незакрытой скобке»

**Почему отвергнуто:** Нарушает принцип единственной ответственности. Движок должен определять невалидные выражения. Скрывание ошибки в движке приведёт к ошибкам при реальном вычислении.

### Альтернатива B: Добавить проверку в `appendCharacter` вместо `tryAutoEvaluate`

**Почему отвергнуто:** `appendCharacter` вызывается из 10+ мест (все кнопки). Проверка в `tryAutoEvaluate` затрагивает только один метод и только тот путь, который вызывает ошибку. Принцип минимального воздействия.

### Альтернатива C: Скрыть ошибку через `clearError()` после `tryAutoEvaluate`

**Почему отвергнуто:** Это маскировка симптома, а не исправление причины. Вычислительный движок будет вызываться зря, а пользователь не увидит ошибку даже при реальной проблеме.

### Альтернатива D: Изменить условие в `guard` на `isDigitOrDecimal(char) || char == "(" || char == ")"`

**Почему отвергнуто:** Альтернатива B — то же самое, но менее масштабно. Если добавить `|| char == ")"` — при вводе «)» автовычисление не вызовется, а должно: `(15+16)` → автовычисление показывает `31`. Нужна именно проверка баланса скобок, а не исключение символов.
