# Анализ ошибки памяти omlx сервера

**Дата:** 2026-07-06  
**Агент:** MimoCode  
**Проблема:** Ошибка нехватки памяти при работе с локальной моделью в OpenCode

---

## Описание проблемы

При работе через OpenCode с локальной моделью `AtomicChat-Ornith-35b-MLX-8bit` на omlx сервере возникает ошибка:

```
Prefill would require ~54.35 GB peak (current 47.31 GB + KV+SDPA 7.04 GB) 
but dynamic ceiling is 54.09 GB. Close other apps to free RAM 
(static cap is 58.00 GB but only 6.78 GB is reclaimable right now), 
raise memory_guard_tier (safe → balanced → aggressive), or reduce context length.
```

Ошибка возникает примерно при достижении 110k токенов из доступных ~200k.

---

## Анализ причины

### Математика потребления памяти

| Компонент | Потребление |
|-----------|-------------|
| Веса модели 35B @ 8-bit | ~35 GB |
| Текущее потребление (overhead + фрагментация) | ~47.31 GB |
| KV-кэш при 110k токенов | ~7.04 GB |
| **Итого при 110k** | **~54.35 GB** |
| Динамический потолок (balanced) | 54.09 GB |
| Статический потолок (sysctl) | 58 GB |

**Ключевая проблема:** KV-кэш растет линейно с длиной контекста. При 200k токенов он составит ~14 GB, что превысит даже статический потолок.

---

## Решения

### 1. Использовать `--memory-guard aggressive` (рекомендуется)

Самое простое решение. Поднимает динамический потолок ближе к статическому (58 GB).

```bash
sudo sysctl iogpu.wired_limit_mb=58000 && OMLX_TRUST_REMOTE_CODE=true omlx serve \
--model /Users/kgate/Models/AtomicChat-Ornith-35b-MLX-8bit \
--host 0.0.0.0 \
--port 8080 \
--memory-guard aggressive
```

### 2. Установить кастомный memory-guard-gb

Явно указать потолок, например 57 GB, чтобы оставить запас:

```bash
--memory-guard-gb 57
```

### 3. Ограничить контекст в конфиге OpenCode

Файл: `/Users/kgate/.config/opencode/opencode.json`

Добавить лимит контекста в секцию модели:

```json
"AtomicChat-Ornith-35b-MLX-8bit": {
  "name": "AtomicChat Ornith 35b MLX 8bit",
  "limit": {
    "context": 100000,
    "output": 8192
  }
}
```

### 4. Закрыть другие приложения

Система сообщает "only 6.78 GB is reclaimable" — этого мало. Закрытие браузера, Slack и других тяжелых приложений может освободить RAM.

### 5. Использовать 6-bit квантизацию

Модель `AtomicChat-Ornith-35b-MLX-6bit` уже доступна. Переход на 6-bit сэкономит ~7-8 GB на весах модели и позволит работать с полным контекстом.

---

## Рекомендация

**Оптимальная комбинация:**
- Использовать `--memory-guard aggressive`
- Ограничить контекст до ~120k в конфиге OpenCode

Для полного 200k контекста — перейти на 6-bit квантизацию.

---

## Дополнительная информация

Доступные опции `omlx serve` для управления памятью:

- `--memory-guard {safe,balanced,aggressive}` — уровень защиты памяти
- `--memory-guard-gb MEMORY_GUARD_GB` — кастомный потолок в GB
- `--paged-ssd-cache-dir` — SSD кэш для префиксного кэширования
- `--hot-cache-max-size` — горячий кэш в памяти
- `--initial-cache-blocks` — предварительное выделение блоков кэша

---

Что делает --paged-ssd-cache-dir

Это префиксный кэш KV-состояний на SSD. Вот как это работает:

Принцип работы
1. Prefix caching — при повторном использовании одинаковых префиксов (например, системного промпта или загруженных файлов) omlx может переиспользовать ранее вычисленные KV-состояния вместо их повторного вычисления.
2. Paged storage — KV-состояния разбиваются на блоки и хранятся на SSD, а не в RAM. Это позволяет кэшировать гораздо больше данных, чем поместится в памяти.

Что это даст тебе
Преимущество	Описание
Ускорение повторных запросов	Если ты отправляешь запрос с тем же префиксом (системный промпт, файлы проекта), inference начнется быстрее
Экономия VRAM/RAM	Кэшированные KV-блоки хранятся на SSD, а не занимают оперативную память
Больше контекста	Можно хранить больше précomputed KV-состояний без переполнения памяти

Пример использования
sudo sysctl iogpu.wired_limit_mb=58000 && OMLX_TRUST_REMOTE_CODE=true omlx serve \
--model /Users/kgate/Models/AtomicChat-Ornith-35b-MLX-8bit \
--host 0.0.0.0 \
--port 8080 \
--memory-guard aggressive \
--paged-ssd-cache-dir /Users/kgate/.omlx/ssd-cache \
--paged-ssd-cache-max-size 50GB \
--hot-cache-max-size 8GB

Важный нюанс
Это не решает твою проблему напрямую. Префиксный кэш помогает с:
- Повторным использованием KV-состояний (не нужно пересчитывать)
- Хранением избыточных KV на SSD
Но он не уменьшает потребление памяти во время текущего inference. Если контекст уже не влезает в RAM — кэш не поможет.

Когда это полезно
- Если у тебя много коротких запросов с общим префиксом (системный промпт + файлы проекта)
- Если SSD быстрый (NVMe) — тогда обращения к кэшу не будут узким местом
- Если хочешь кэшировать состояния для повторного использования между сессиями

Для твоей ситуации (один длинный контекст ~110k+) это не критично, но может немного ускорить работу за счёт переиспользования précomputed KV для префиксов.

## Все ключи omlx serve, влияющие на память

### Прямое управление памятью

| Ключ | Описание | Как помогает |
|------|----------|--------------|
| `--memory-guard aggressive` | Поднимает динамический потолок ближе к статическому | **Главный ключ** — даёт больше RAM для модели и KV-кэша |
| `--memory-guard-gb 57` | Кастомный потолок в GB | Точная настройка — можно выставить ровно столько, сколько нужно |
| `--max-concurrent-requests 1` | Ограничение параллельных запросов | Каждый запрос держит свой KV-кэш. Один запрос = меньше памяти |

### Управление кэшем

| Ключ | Описание | Как помогает |
|------|----------|--------------|
| `--hot-cache-max-size 4GB` | Размер горячего кэша в RAM | Ограничивает, сколько KV-состояний хранится в памяти |
| `--paged-ssd-cache-dir /path` | Вынос KV на SSD | Освобождает RAM за счёт хранения на диске |
| `--paged-ssd-cache-max-size 50GB` | Лимит SSD-кэша | Контролирует размер кэша на диске |
| `--initial-cache-blocks 128` | Предварительное выделение блоков | Меньше блоков = меньше начальное потребление (по умолчанию 256) |
| `--no-cache` | Отключить SSD-кэш | Если кэш не нужен — не тратит ресурсы на его управление |

### Оптимальная комбинация для твоего случая

```bash
sudo sysctl iogpu.wired_limit_mb=58000 && OMLX_TRUST_REMOTE_CODE=true omlx serve \
--model /Users/kgate/Models/AtomicChat-Ornith-35b-MLX-8bit \
--host 0.0.0.0 \
--port 8080 \
--memory-guard aggressive \
--max-concurrent-requests 1 \
--initial-cache-blocks 128 \
--hot-cache-max-size 4GB \
--paged-ssd-cache-dir /Users/kgate/.omlx/ssd-cache \
--paged-ssd-cache-max-size 50GB
```

### Что делает каждая настройка в этой комбинации

1. **`--memory-guard aggressive`** — maximum RAM для модели
2. **`--max-concurrent-requests 1`** — только один запрос за раз, не дублирует KV-кэш
3. **`--initial-cache-blocks 128`** — меньше начальное выделение (вместо 256)
4. **`--hot-cache-max-size 4GB`** — ограничивает горячий кэш в памяти
5. **`--paged-ssd-cache-dir`** — выгружает избыточные KV на SSD

### Ключи, которые НЕ помогают с памятью

| Ключ | Почему не помогает |
|------|-------------------|
| `--embedding-batch-size` | Только для embedding-моделей, не для inference |
| `--sse-keepalive-mode` | Только для SSE-соединений, не влияет на память |
| `--mcp-config` | Только для MCP-интеграции |
| `--hf-endpoint` | Только для загрузки моделей |
| `--http-proxy` | Сетевые настройки |
| `--base-path` | Путь к данным, не влияет на память |
