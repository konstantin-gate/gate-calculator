## 1. Постановка задачи

### 1.1. Цель

Обеспечить копирование содержимого **главного поля вывода** дисплея калькулятора при нажатии ⌘C **в любой момент времени** — независимо от того, какой элемент UI является first responder.

### 1.2. Две составляющие проблемы

**Проблема A — Доставка события (dispatch):**

Текущая реализация Cmd+C находится в `KeyHandlerNSView.performKeyEquivalent(with:)`. Этот метод вызывается AppKit-системой **только** когда `KeyHandlerNSView` является first responder. Когда пользователь нажимает на кнопку калькулятора или область дисплея —焦点 (first responder) переходит к этому элементу UI, и `KeyHandlerNSView` перестаёт получать клавиатурные события. ⌘C игнорируется.

**Проблема B — Неполные данные (data):**

Даже если бы dispatch работал безупречно, метод `copyResult()` копирует **только** свойство `result` (отформатированный результат вычисления). Если на дисплее отображается выражение (пока не нажат `=`), текст ошибки или начальное значение "0" — копирования не происходит, потому что `result == nil`.

### 1.3. Ожидаемое поведение после исправления

| Состояние дисплея | Копируемое значение | Пример |
|---|---|---|
| Пустой дисплей | `"0"` | `0` |
| Ввод выражения | Текст выражения (ASCII) | `15+16` |
| Результат вычисления | Отформатированный результат | `31` |
| Ошибка | Текст ошибки | `Деление на ноль` |

**Примечание:** При копировании выражения копируется **сырой ASCII-текст** (например `15+16`), а не форматированное отображение (например `15 ÷ 16`). Это необходимо для корректной вставки обратно через ⌘V.

## 3. Архитектурное обоснование решения

### 3.1. Почему `.onCommand` — правильный способ перехвата ⌘C

**Альтернативы и причины их отклонения:**

| Альтернатива | Почему отклонена |
|---|---|
| Оставить `performKeyEquivalent` без изменений | Работает **только** когда `KeyHandlerNSView` — first responder. После нажатия на кнопку/дисплей焦点 уходит, ⌘C перестаёт работать |
| Сделать все кнопки первыми респондентами с `keyDown` | Каждая кнопка должна была бы обрабатывать ⌘C — дублирование логики, нарушение SRP |
| Использовать `NSEvent.addGlobalMonitorForEvents` | Глобальный монитор перехватывает события **вне** приложения, не подходит для внутриприкладного перехвата. Также не рекомендуется Apple для обработки команд |
| Использовать `.keyboardShortcut()` на кнопке | Привязывает команду к конкретной кнопке UI, а не ко всему view-дереву. ⌘C должен работать при фокусе на любом элементе |

**Почему `.onCommand` — верно:**

1. `.onCommand(key:modifiers:action:)` — стандартный модификатор SwiftUI для перехвата клавиатурных команд на уровне view-дерева
2. Работает **независимо от first responder** — команда перехватывается до передачи в AppKit first responder chain
3. Перехватывает как клавиатурные сочетания, так и команды из меню (если в будущем будет добавлен пункт меню «Копировать»)
4. Не требует изменения архитектуры `KeyHandlerNSView`
5. Не нарушает MVVM — логика копирования остаётся в `CalculatorViewModel`

**Сигнатура метода (из документации Apple, macOS 14.0+):**
```swift
func onCommand(key: KeyEquivalent, modifiers: EventModifiers, action: @escaping () -> Void) -> some View
```

**Доступность:** macOS 14.0+ (Sonoma) — является минимальной версией проекта (подтверждено в `AGENTS.md:7` и `Package.swift`).

### 3.2. Почему `displayValue` — правильный способ определения копируемых данных

**Альтернативы и причины их отклонения:**

| Альтернатива | Почему отклонена |
|---|---|
| Дублировать логику из `DisplayView` (включая `.replacingOccurrences(of: "/", with: " ÷ ")`) | DisplayView содержит **визуальное** форматирование (замена `/` на `÷`, `*` на `×`, запятые). Для копирования нужны **сырые данные**, иначе вставка через ⌘V будет содержать символы `÷` и `×`, которые движок не распознает |
| Передавать отображаемое значение из View в ViewModel | Нарушает MVVM — ViewModel не должен зависеть от View |
| Копировать `expression` + `result` + `errorMessage` в `copyResult()` без computed property | Дублирование логики приоритетов, которую придётся поддерживать в двух местах (ViewModel и DisplayView) |

**Почему `displayValue` — верно:**

1. Computed property определяет **один источник истины** для «что сейчас показано на дисплее»
2. Логика `result ?? (expression.isEmpty ? "0" : expression)` дублирует строку 58 `DisplayView.swift` **в ViewModel** — это стандартный MVVM-паттерн (business logic в ViewModel, отображение в View)
3. `displayValue` возвращает `String` (не optional) — гарантированно непустая строка, что упрощает вызывающий код
4. Вычисление **синхронное и дешёвое** — три проверки nil/пустоты, без обращения к движку или сервисам

## 12. Итоговое резюме

**Проблема:** ⌘C не копировал содержимое дисплея по двум причинам: (A) событие не доставлялось `KeyHandlerNSView` при потере first responder; (B) метод `copyResult()` копировал только `result`, игнорируя выражение, ошибку и начальное значение.

**Решение:** Добавить `.onCommand(key: "c", modifiers: .command)` в `CalculatorContentView` для гарантированного перехвата ⌘C, и добавить computed property `displayValue` в `CalculatorViewModel` для определения полного содержимого дисплея.

**Затронутые файлы:** 2
- `Sources/App/CalculatorApp.swift` (+3, −4 строки)
- `Sources/ViewModels/CalculatorViewModel.swift` (+10, −1 строка)

**Незатронутые файлы:** Все остальные файлы проекта (подтверждено: раздел 6.3).

**Регрессии:** Отсутствуют. Все клавиатурные комбинации (⌘V, ⌘A, ⌘Z), ввод символов, вычисления, история и память продолжают работать без изменений.
