# 3. Главная цель проекта

Создать современный нативный калькулятор для macOS.

После запуска пользователь должен подумать:

> «Это выглядит как системный Calculator.app, но наконец-то умеет делать то, чего всегда не хватало.»

Именно такое впечатление является главной целью проекта.

---

# 4. Главная проблема, которую решает приложение

Современный системный Calculator.app в macOS имеет ограничение.

Пользователь не может просто вставить математическое выражение:

```
(15+16+17+18)/4
```

и сразу получить ответ.

Вместо этого приходится:

* вводить выражение вручную;
* использовать сторонние приложения;
* открывать инженерные калькуляторы;
* использовать блокноты для вычислений;
* использовать терминал.

Это ухудшает пользовательский опыт.

Настоящее приложение существует исключительно для устранения этого недостатка.

# 6. Основные принципы

Все дальнейшие решения должны удовлетворять следующим принципам.

---

## Простота

Любая функция должна существовать только при наличии реальной пользовательской ценности.

Каждая новая возможность увеличивает сложность.

Если функция не улучшает повседневную работу пользователя, она должна быть исключена.

---

## Минимализм

Минимум настроек.

Минимум элементов.

Минимум отвлекающих факторов.

Минимум режимов.

---

## Предсказуемость

Пользователь должен заранее понимать результат любого действия.

Интерфейс не должен удивлять.

Он должен вести себя именно так, как ожидает пользователь macOS.

---

## Скорость

Каждое действие должно восприниматься мгновенным.

Целевое время реакции интерфейса:

менее 16 мс.

---

## Нативность

Каждый элемент интерфейса должен ощущаться частью macOS.

Запрещается создавать ощущение стороннего приложения.

---

## Последовательность

Во всем приложении используются единые правила:

* одинаковые анимации;
* одинаковые размеры;
* одинаковые интервалы;
* одинаковые принципы взаимодействия.

---

## Незаметность

Самое лучшее приложение — то, которое пользователь перестает замечать.

Он думает о вычислениях, а не об интерфейсе.

# 12. Критерий успеха проекта

Проект считается успешным, если пользователь сможет выполнить следующий сценарий без каких-либо инструкций:

1. Открыть приложение.
2. Нажать ⌘V.
3. Вставить:

```
(15+16+17+18)/4
```

4. Мгновенно увидеть правильный результат.
5. Закрыть приложение с ощущением, что именно так и должен работать системный калькулятор macOS.

Если этот сценарий выполняется естественно, быстро и без необходимости изучать интерфейс, главная цель проекта достигнута.

# 13. Технологический стек

Выбор технологий является частью архитектуры приложения.

Любая замена перечисленных ниже технологий требует веского технического обоснования.

Главный принцип:

**использовать исключительно современные нативные технологии Apple.**

---

## 13.1 Язык программирования

Обязательно использовать:

* Swift 6

Использовать исключительно современные возможности языка.

Следовать:

* Swift API Design Guidelines
* Swift Concurrency Best Practices

Избегать устаревших конструкций.

---

## 13.2 Пользовательский интерфейс

Основной UI-фреймворк:

* SwiftUI

Использовать современные API.

Использовать:

* Observation
* @Observable
* @Bindable
* @MainActor там, где это действительно необходимо.

Не использовать устаревший ObservableObject без объективной причины.

---

## 13.3 AppKit

AppKit допускается исключительно в случаях, когда SwiftUI пока не предоставляет полноценного решения.

Каждое использование AppKit должно иметь комментарий с объяснением причины.

Запрещается писать приложение целиком на AppKit.

---

## 13.4 Архитектурный стиль

Обязательно использовать MVVM.

Допускается применение небольших Coordinator-подобных компонентов при необходимости.

Не использовать чрезмерно сложные архитектуры.

Не применять VIPER.

Не применять Redux.

Не применять TCA, если его преимущества не оправдывают увеличение сложности проекта.

Главная цель — простая, понятная и легко сопровождаемая архитектура.

---

## 13.5 Зависимости

Минимизировать количество сторонних библиотек.

Предпочитать стандартные библиотеки Apple.

Каждая внешняя зависимость должна быть документирована и обоснована.

Если функциональность можно реализовать средствами Foundation или Swift Standard Library, использовать именно их.

# 14. Общие архитектурные принципы

Архитектура должна проектироваться с учетом длительной поддержки проекта.

"You Aren't Gonna Need It (YAGNI)"

Предпочитать код, который легче читать.

Даже если он занимает больше строк.

Избегать скрытого поведения.

Избегать сложных цепочек модификаторов.

Избегать трудно прослеживаемой логики.

## Композиция выше наследования

Предпочитать композицию.

## Локальность изменений

Изменение одной функции приложения не должно требовать изменений во множестве файлов.

Каждый модуль должен иметь четко определенную ответственность.

# 21. Вычислительный движок (Calculator Engine)

## Назначение

Calculator Engine является ядром приложения.

Он отвечает исключительно за:

* разбор математического выражения;
* проверку корректности;
* вычисление результата;
* возврат результата или структурированной ошибки.

Engine не должен содержать:

* пользовательский интерфейс;
* зависимости от SwiftUI;
* зависимости от AppKit;
* работу с буфером обмена;
* работу с историей;
* форматирование отображения.

Engine должен быть полностью независимым модулем.

В идеале он должен собираться и тестироваться отдельно от остального приложения.

---

# 22. Архитектура Calculator Engine

Рекомендуемая структура:

```text
CalculatorEngine/

    Tokenizer/

        Token.swift
        Tokenizer.swift

    Parser/

        Parser.swift
        Operator.swift
        Precedence.swift

    AST/

        ExpressionNode.swift

    Evaluator/

        Evaluator.swift

    Errors/

        CalculatorError.swift
```

Каждый модуль имеет одну ответственность.

---

# 23. Требования к вычислительному движку

Engine обязан:

* работать детерминированно;
* быть полностью повторяемым;
* не использовать глобальное состояние;
* быть потокобезопасным;
* не хранить внутреннее состояние между вычислениями.

Каждый вызов вычисления должен быть независимым.

# 33. Ошибки парсинга

Парсер обязан корректно обнаруживать:

лишнюю закрывающую скобку;

незакрытую скобку;

неизвестный символ;

двойной оператор;

пустое выражение;

некорректное число;

несколько десятичных разделителей;

деление на ноль;

неожиданный конец выражения.

Ошибки должны быть структурированными.

---

Например:

```swift
enum CalculatorError: Error {
    case unexpectedToken
    case missingClosingParenthesis
    case divisionByZero
    case invalidNumber
    case emptyExpression
}
```

Допускается иная структура, если она обеспечивает такую же ясность.

---

# 34. Отображение ошибок

Пользователь никогда не должен видеть:

stack trace;

debug information;

Swift Error;

NSError.

Пользователь должен видеть понятные сообщения.

Например:

"Неверное выражение"

"Пропущена закрывающая скобка"

"Деление на ноль"

"Неожиданный символ"

Сообщения должны быть локализуемыми.

---

# 35. Числовая модель

Рекомендуется использовать Decimal вместо Double там, где это практически оправдано, чтобы уменьшить влияние ошибок двоичной арифметики при обычных пользовательских вычислениях.

Если для отдельных операций выбран Double, это решение должно быть осознанным, документированным и не ухудшать пользовательский опыт.

Вне зависимости от выбранного внутреннего типа пользователь не должен сталкиваться с артефактами вроде:

```text
0.30000000000000004
```

или

```text
14.999999999999998
```

---

# 36. Форматирование результата

Отображаемый результат должен быть человекочитаемым.

Например:

правильно

```text
15
```

не

```text
15.0
```

правильно

```text
0.5
```

не

```text
0.5000000000000
```

Удалять незначащие нули.

Использовать локализованный формат отображения чисел.

Поддерживать разделители тысяч (если включены в настройках).

---

# 37. Производительность

Вычисление обычного выражения должно восприниматься мгновенным.

Даже длинные выражения из нескольких сотен токенов должны вычисляться без заметной задержки.

Парсер не должен выполнять лишних проходов по данным.

Избегать ненужных копирований массивов и строк.

---

# 38. Буфер обмена

Поддержка буфера обмена является одной из ключевых функций приложения.

Она должна ощущаться абсолютно естественной.

---

## Вставка выражения

Если пользователь нажимает:

⌘V

или выбирает:

Edit → Paste

или использует контекстное меню,

и в буфере находится корректное математическое выражение, приложение должно:

1. вставить выражение;
2. немедленно распознать его;
3. вычислить;
4. обновить дисплей.

Никаких дополнительных действий не требуется.

---

## Поддерживаемые варианты

Все перечисленные варианты должны работать:

```text
15+16
```

```text
15 +16
```

```text
15+ 16
```

```text
15 + 16
```

```text
((15+16)*4)/7
```

```text
-(15+16)
```

---

## Если вставлено число

Если в буфере находится только число:

```text
125
```

то оно должно просто стать текущим значением.

---

## Если вставлен мусор

Если вставлен текст:

```text
Hello World
```

или

```text
Apple Inc.
```

или произвольная строка, не являющаяся математическим выражением, приложение не должно аварийно завершаться.

Оно должно:

* проигнорировать вставку;
* либо показать локализованное сообщение о невозможности вычисления.

Поведение должно быть единообразным и документированным.

---

## Drag & Drop

Желательно поддерживать перетаскивание текстового выражения непосредственно в окно приложения.

Если перетащенный объект содержит допустимое выражение, оно должно быть обработано так же, как при вставке через буфер обмена.

# Acceptance Criteria

Подсистема вычислений считается соответствующей требованиям, если:

* выражения любой разумной длины вычисляются корректно;
* пробелы не влияют на результат;
* вложенные скобки работают без ограничений, кроме разумных технических пределов;
* все синтаксические ошибки обнаруживаются и отображаются корректно;
* вычисления не вызывают зависаний интерфейса;
* пользователь может вставить выражение через ⌘V и получить результат без дополнительных действий;
* формат результата соответствует ожиданиям обычного пользователя, а не внутреннему представлению чисел.

уменьшает размер шрифта;

позволяет горизонтальную прокрутку;

# Acceptance Criteria

Пользовательский интерфейс считается соответствующим требованиям, если:

* при первом запуске создаётся ощущение нативного приложения macOS;
* внешний вид не выглядит как стилизация под Apple, а воспринимается как естественное продолжение системной дизайн-системы;
* интерфейс остаётся аккуратным и читаемым при изменении размеров окна;
* Light Mode и Dark Mode поддерживаются без визуальных артефактов;
* все элементы имеют предсказуемые состояния (обычное, hover, pressed, focus);
* дисплей остаётся читаемым даже при длинных выражениях;
* анимации помогают восприятию интерфейса и не отвлекают пользователя;
* отсутствуют визуальные решения, выбивающиеся из современного языка дизайна macOS.

---

# 64. Пользовательский опыт (User Experience)

## Общая философия UX

Главная задача UX — сделать работу с приложением настолько естественной, чтобы пользователь никогда не задумывался о том, **как** выполнить действие.

Любое действие должно быть очевидным.

Пользователь не должен изучать интерфейс.

Не должен читать инструкцию.

Не должен открывать справку.

Не должен смотреть обучающие видео.

Если приложение требует объяснений, значит UX требует переработки.

---

# 65. Основной пользовательский сценарий

Это самый важный сценарий проекта.

Именно под него оптимизируется вся архитектура приложения.

### Сценарий

Пользователь:

1. открывает приложение;

2. нажимает

⌘V

3. вставляет

```text
(15+16+17+18)/4
```

4. немедленно получает

```text
16.5
```

Никаких дополнительных действий.

Не требуется нажимать "=".

Не требуется выбирать режим.

Не требуется активировать поле ввода.

Не требуется подтверждение.

Весь сценарий должен занимать менее одной секунды.

---

# 66. Вторичный сценарий

Обычное использование мышью.

Пользователь нажимает кнопки.

Получает привычное поведение обычного калькулятора.

Если он никогда не пользуется буфером обмена —

он вообще не замечает, что приложение отличается от Calculator.app.

---

# 67. Работа с клавиатурой

Полноценная клавиатурная поддержка обязательна.

Пользователь должен иметь возможность пользоваться приложением вообще без мыши.

Поддерживаются:

цифры

*

-

*

/

%

(

)

.

Enter

Return

Delete

Backspace

Esc

Tab

Shift+Tab

⌘C

⌘V

⌘A

⌘Z (если действие действительно можно отменить)

Стандартные сочетания клавиш должны вести себя так, как ожидает пользователь macOS.

---

# 68. Поведение клавиши Enter

Нажатие Enter или Return должно:

вычислить выражение;

обновить дисплей;

добавить запись в историю (если вычисление успешно);

при необходимости подготовить приложение к вводу следующего выражения.

Поведение должно быть единообразным.

---

# 69. Поведение клавиши Escape

Esc очищает текущее выражение.

Если выражение уже пустое —

очищает отображаемый результат (при необходимости).

Поведение должно быть документировано и оставаться постоянным.

---

# 70. Поведение Backspace

Удаляется последний введённый символ.

Если удаление делает выражение пустым —

приложение возвращается в исходное состояние без ошибок.

Удаление должно быть мгновенным.

---

# 71. Буфер обмена

Буфер обмена является основной особенностью приложения.

Он должен ощущаться частью системы.

---

## Вставка

При вставке математического выражения:

1. выражение автоматически появляется на дисплее;

2. автоматически вычисляется;

3. результат отображается немедленно.

---

## Вставка числа

Если вставлено одно число —

оно становится текущим выражением.

Никаких дополнительных преобразований.

---

## Вставка некорректного текста

Если вставленный текст невозможно интерпретировать как математическое выражение —

приложение не должно:

издавать системный звук;

открывать Alert;

блокировать пользователя;

показывать технические ошибки.

Следует использовать небольшое локализованное сообщение внутри интерфейса.

---

# 72. Копирование

Команда Copy должна работать максимально естественно.

Если пользователь скопировал результат —

в буфер попадает только результат.

Например:

```text
16.5
```

Если в будущем будет реализовано выделение выражения —

копироваться должно именно выделенное содержимое.

---

# 73. Автоматическое копирование результата

Опциональная настройка.

Если пользователь включил её —

после успешного вычисления результат автоматически помещается в буфер обмена.

По умолчанию функция отключена.

Она не должна менять основной сценарий работы.

---

# 74. История вычислений

История должна быть максимально простой.

Она не является основной функцией приложения.

История существует только для удобства.

---

## История содержит

выражение;

результат;

дату и время (необязательно отображать по умолчанию).

---

## Размер истории

По умолчанию рекомендуется хранить последние 50 вычислений.

Размер должен быть легко изменяемым в коде.

---

## Просмотр истории

История открывается ненавязчиво.

Не отдельным окном.

Не полноэкранным режимом.

Предпочтительно:

popover;

sheet;

выдвижная боковая панель (если она не нарушает минимализм).

Главное —

не усложнить основной сценарий.

---

## Повторное использование

Пользователь может нажать на запись истории.

Выражение возвращается на дисплей.

При необходимости сразу вычисляется повторно.

---

# 75. Настройки

Настройки должны быть минимальными.

Их количество должно стремиться к нулю.

Рекомендуемые настройки:

автоматически копировать результат;

показывать разделители тысяч;

максимальное количество знаков после запятой (при необходимости);

размер истории;

очистить историю.

Добавление новых настроек требует серьёзного обоснования.

---

# 76. Первое открытие приложения

Первый запуск должен быть полностью готов к работе.

Не показывать:

обучение;

мастер настройки;

экран приветствия;

советы;

маркетинговые окна.

Пользователь сразу видит калькулятор.

И сразу может работать.

---

# 77. Поведение после запуска

После открытия приложения:

фокус ввода должен быть готов к работе;

можно сразу печатать;

можно сразу вставлять выражение;

можно сразу пользоваться клавиатурой.

Никаких дополнительных кликов.

---

# 78. Сохранение состояния

После закрытия приложения желательно сохранить:

размер окна;

позицию окна;

выбранную тему (если отличается от системной);

настройки;

историю.

Текущее незавершённое выражение можно восстанавливать только в том случае, если это не приводит к неожиданному поведению.

---

# 79. Микровзаимодействия

Микровзаимодействия должны быть едва заметными.

Например:

небольшое изменение материала кнопки;

лёгкое изменение прозрачности;

короткая анимация обновления результата;

мягкое появление сообщения об ошибке.

Запрещаются:

прыгающие элементы;

резкие вспышки;

сложные переходы;

декоративные эффекты.

---

# 80. Сообщения об ошибках

Ошибки должны восприниматься спокойно.

Они не должны создавать ощущение, что приложение "сломалось".

Сообщение должно:

быть коротким;

понятным;

локализуемым;

не обвинять пользователя.

Например:

"Неверное выражение"

лучше, чем

"Ошибка синтаксического анализа."

---

# 81. Локализация

Архитектура приложения должна изначально учитывать возможность локализации.

Все пользовательские строки должны быть вынесены в локализуемые ресурсы.

Не допускается наличие "захардкоженного" текста в интерфейсе.

Минимальный набор языков:

English

Русский

Архитектура должна позволять безболезненно добавлять новые языки.

---

# 82. Accessibility

Приложение должно корректно работать с системными средствами доступности.

Необходимо поддерживать:

VoiceOver;

полноценную клавиатурную навигацию;

системные настройки контрастности;

Reduce Motion;

увеличенный размер интерфейсных элементов там, где это применимо.

Каждый интерактивный элемент должен иметь понятное accessibilityLabel и, при необходимости, accessibilityHint.

---

# 83. Производительность пользовательского интерфейса

Интерфейс должен оставаться отзывчивым при любых допустимых действиях пользователя.

Любые потенциально длительные операции не должны блокировать главный поток.

При обновлении интерфейса следует минимизировать количество перерисовок и вычислений.

---

# 84. Конфиденциальность

Приложение должно работать полностью локально.

Запрещается:

отправка пользовательских данных;

телеметрия;

аналитика;

сбор истории вычислений на внешние серверы;

сетевые запросы, не связанные с явной функцией приложения.

Если приложению не требуется интернет — оно не должно обращаться в сеть.

---

# Acceptance Criteria

UX считается соответствующим требованиям, если:

* пользователь способен начать работу сразу после запуска приложения;
* основной сценарий "⌘V → результат" выполняется без дополнительных действий;
* приложение полностью управляется с клавиатуры;
* история не отвлекает от основной задачи, но доступна при необходимости;
* сообщения об ошибках понятны и не нарушают рабочий процесс;
* настройки остаются минимальными и не перегружают интерфейс;
* приложение ведёт себя предсказуемо и соответствует ожиданиям пользователя macOS.

---

# 85. Производительность

## Общие требования

Производительность рассматривается как одна из ключевых характеристик качества приложения.

Пользователь никогда не должен ждать выполнения обычной операции.

Любое действие должно восприниматься мгновенным.

---

## Время запуска

Приложение должно запускаться максимально быстро.

После запуска пользователь должен сразу иметь возможность:

* вводить выражение;
* вставлять выражение;
* пользоваться клавиатурой.

Не допускается блокировка интерфейса во время инициализации.

---

## Отзывчивость интерфейса

Все операции пользовательского интерфейса должны выполняться на главном потоке только тогда, когда это действительно необходимо.

Вычисления, не требующие обновления интерфейса, не должны приводить к заметным задержкам или "подвисаниям".

---

## Использование памяти

Приложение должно использовать разумный объём памяти.

Не допускается:

* бесконтрольный рост памяти;
* утечки памяти;
* retain cycle;
* хранение ненужных объектов;
* бесконечный рост истории вычислений.

---

# 86. Swift Concurrency

Проект должен использовать современную модель конкурентности Swift.

Использовать:

* async/await;
* actor там, где это действительно улучшает потокобезопасность;
* Sendable для подходящих типов;
* @MainActor только для компонентов, непосредственно связанных с пользовательским интерфейсом.

Не использовать GCD напрямую без объективной необходимости.

Избегать смешивания нескольких моделей конкурентности.

---

# 87. Безопасность

Несмотря на локальный характер приложения, необходимо соблюдать хорошие инженерные практики.

Приложение должно быть устойчиво к:

* некорректному пользовательскому вводу;
* очень длинным выражениям;
* неожиданным символам;
* пустому буферу обмена;
* повреждённым данным истории;
* неожиданному завершению работы.

Ни один из этих сценариев не должен приводить к аварийному завершению приложения.

---

# 88. Логирование

В Release-сборке логирование должно быть минимальным.

Не выводить:

* внутренние структуры данных;
* содержимое пользовательских выражений без необходимости;
* диагностические сообщения разработки.

Для отладочных сборок допускается расширенное логирование.

---

# 89. Тестирование

## Общие требования

Каждый модуль должен иметь автоматические тесты.

Минимальные категории тестов:

* Unit Tests;
* UI Tests.

---

## Unit Tests

Необходимо протестировать:

Tokenizer

Parser

Evaluator

Clipboard Parser

Formatting

History

Utilities

Особое внимание уделить пограничным случаям.

Например:

пустая строка;

одно число;

очень длинное выражение;

глубоко вложенные скобки;

деление на ноль;

несколько операторов подряд;

некорректный ввод;

отрицательные числа;

проценты.

---

## UI Tests

Проверить:

открытие приложения;

ввод с клавиатуры;

нажатия кнопок;

вставку выражения;

копирование результата;

отображение ошибок;

историю;

работу Light Mode;

работу Dark Mode.

---

## Regression Tests

Каждая найденная ошибка должна сопровождаться тестом, предотвращающим её повторное появление.

---

# 90. Code Quality

Код должен быть написан так, словно его будет поддерживать другая команда разработчиков.

Следовать следующим принципам:

* SOLID (там, где это оправдано);
* KISS;
* DRY;
* YAGNI.

Не применять шаблоны проектирования без реальной необходимости.

---

## Именование

Все имена должны быть понятными.

Не использовать сокращения без необходимости.

Предпочитать полные, читаемые названия.

---

## Размер функций

Функции должны быть небольшими.

Каждая функция должна выполнять одну логически завершённую задачу.

---

## Размер типов

Избегать чрезмерно больших View, ViewModel и сервисов.

Если тип становится слишком большим, необходимо пересмотреть его ответственность.

---

## Документация

Документировать:

* публичные API;
* сложные алгоритмы;
* архитектурные решения.

Не документировать очевидный код.

Комментарии должны объяснять **почему**, а не **что** делает код.

---

# 91. Definition of Done

Работа считается завершённой только при выполнении всех условий ниже.

## Архитектура

# 94. Итоговые Acceptance Criteria

Проект считается полностью успешным только в том случае, если выполняются все следующие условия:

1. Пользователь открывает приложение и сразу понимает, как им пользоваться.

2. Пользователь может вставить математическое выражение через ⌘V и мгновенно получить корректный результат.

3. Пользователь может полностью управлять приложением с клавиатуры.

4. Интерфейс выглядит и ощущается как современное нативное приложение macOS.

5. Приложение не содержит лишних функций и остаётся сфокусированным на своей единственной задаче.

6. Архитектура проекта проста, понятна и пригодна для долгосрочной поддержки.

7. Код соответствует современным рекомендациям Apple, Swift API Design Guidelines и принципам качественной инженерной разработки.

8. Приложение работает полностью локально, не требует подключения к сети и уважает конфиденциальность пользователя.

9. После нескольких дней использования пользователь воспринимает приложение не как сторонний инструмент, а как естественную замену системному Calculator.app.

10. Главная цель проекта достигнута только в том случае, если пользователь искренне задаётся вопросом:

> «Почему Apple сама до сих пор не сделала именно так?»

# Заключение

Настоящая спецификация определяет не только функциональность приложения, но и философию его разработки.

При возникновении любого спорного вопроса приоритет требований должен быть следующим:

1. Простота для пользователя.
2. Соответствие современному UX macOS.
3. Соответствие Apple Human Interface Guidelines.
4. Производительность.
5. Поддерживаемость кода.
6. Расширяемость архитектуры.

Любое решение, противоречащее этим принципам, должно быть пересмотрено до начала реализации.

Конечной целью является создание приложения, которое ощущается как недостающее звено в экосистеме macOS: максимально нативного, минималистичного, производительного и удобного калькулятора с полноценной поддержкой математических выражений и буфера обмена.
