## 2. Критические несоответствия (Must Fix)

### C-01. Научный режим — прямое нарушение Section 11

**SRS Section 11 («Категорически запрещено»):**
> Запрещается добавлять: инженерный режим, научный режим, тригонометрию, логарифмы...

**Факт:** `CalculatorView.swift` строки 5-8 реализует `enum CalculatorMode { case standard, scientific }`. Научная сетка (строки 120-183) содержит ~40 научных кнопок: sin⁻¹, cos⁻¹, tan⁻¹, sinh⁻¹, cosh⁻¹, tanh⁻¹, x², x³, xʸ, yˣ, ²√x, ³√x, logᵧ, log₂, x!, EE, и др.

**Статус:** Все научные кнопки — **не реализованы функционально**. Они бросают в `appendFunction()` строковые идентификаторы (`"asin"`, `"sqrt2"` и т.д.), которые никуда не обрабатываются. Это мёртвый код, нарушающий философию минимализма SRS.

**Рекомендация:** Полностью удалить научный режим: `CalculatorMode`, `scientificButtonGrid`, все связанные `ButtonLabel` cases (строки 32-50 в CalculatorButton.swift), и обработчики в `handleButtonPress()`. Кнопка переключения режима в toolbar также должна быть удалена.

### C-04. Проценты — противоречие в SRS Section 32

**SRS Section 32** содержит внутреннее противоречие:

> **Правило 3:** `50 + 10%` = `50 + (50 * 0.10)` = `55.0` (в контексте калькулятора)
> 
> **Выбор модели:** используется математическая модель — Процент всегда означает «делить на 100»

Эти два правила противоречат друг другу:
- Правило 3 даёт: `50 + 10% = 55.0` (процент от левого операнда)
- Математическая модель даёт: `50 + 10% = 50.10` (10 / 100)

**Факт:** Реализация и все тесты следуют **математической модели**:
```swift
// CalculatorEngineTests.swift строка 127-129
func testEvaluate_PercentWithAddition() {
    let result = try engine.evaluate("100+5%")
    XCTAssertEqual(result, Decimal(string: "100.05")!) // 100 + (5/100)
}
```

Это **правильный выбор** — математическая модель консистентна и предсказуема. Правило 3 в SRS Section 32 является ошибкой автора спецификации.

**Рекомендация:** Удалить правило 3 из SRS (упоминание «калькуляторской модели процентов») для устранения путаницы. Текущая реализация верна.

**Рекомендация:** Заменить `.design(.rounded)` на `.design(.default)` или полностью убрать параметр `design` (по умолчанию SF Pro).

### S-02. Размеры шрифтов дисплея не соответствуют спецификации

**SRS Section 42:**
> Результат: SF Pro, 42 pt | Ошибка: SF Pro, 24 pt

**Факт:** `DisplayView.swift` строки 31, 94-98:

**SRS Section 42:**
> Фон цифровых кнопок: secondarySystemBackground | Фон кнопок операций: systemGray5 | Фон кнопки "=": systemBlue

**Факт:** `CalculatorColors.swift` строки 18-32 используют **захардкоженные RGB значения**:

## 4. Замечания средней тяжести (Consider Fix)

### M-01. Мёртвый код: Decimal+Extensions.swift не используется

`Decimal+Extensions.swift` определяет `isZero`, `isNegative`, `absoluteValue`, `displayString`. Ни один из этих свойств **нигде не используется** в кодовой базе. `NumberFormatterService.format()` и `DisplayView` используют собственные форматы.

### M-02. Дублирование: String+Calculator.swift vs ClipboardManager.swift

Оба файла содержат идентичную логику `isMathExpression`:
- `String+Calculator.swift` строки 23-31
- `ClipboardManager.swift` строки 37-45

### M-03. Мёртвый код: EmptyStateView.swift не используется

`EmptyStateView` существует, но `HistoryPanelView` использует `ContentUnavailableView` напрямую (строка 11).

### M-04. Package.swift: несуществующая папка "Models"

`Package.swift` строка 39 перечисляет `"Models"` в источниках `CalculatorApp`, но папки `Sources/Models/` не существует. Это может вызвать предупреждения при сборке.

### M-05. HistoryEntry.timestamp нигде не используется

Структура `HistoryEntry` содержит поле `timestamp: Date` (строка 17), но оно **нигде не отображается** и не используется в логике. SRS Section 75 говорит «необязательно отображать по умолчанию» — ок, но создание метки времени впустую — лишний overhead.

### M-06. Обработка "e" как константы Эйлера конфликтует с экспоненциальной записью

`Tokenizer.swift` строки 96-113: если `e` не предшествует цифре, это константа Эйлера. Но `e3` интерпретируется как число (через `readNumber`). Это означает:
- `"e"` → 2.718... ✅
- `"e3"` → 3 (читается как "e" × 10³ через readNumber, но фактически читает "e3" как числовую строку, которая не парсится в Decimal и возвращает 0)

На самом деле `readNumber` при `"e3"` вернёт `(0, start)` потому что `"e3"` не является валидной Decimal-строкой. Это может привести к тихому возврату нуля вместо ошибки.

### M-07. Precedence.swift: unaryMinus имеет более высокий приоритет чем percent

`Precedence.swift` строки 3-8:
```swift
case addition = 1, multiplication = 2, unaryMinus = 3, percent = 4
```

SRS Section 28 говорит:
> Следующий уровень (левый приоритет): Унарный минус
> Следующий уровень (левый приоритет): *, /, %

Унарный минус и %,/,* должны быть **на одном уровне**, а не разделены. В текущей реализации `percent` (4) имеет более высокий приоритет чем `unaryMinus` (3), что означает: `-5%` вычисляется как `-(5%) = -0.05`, а не `(-5)% = -0.05`. Результат совпадает, но семантика неверна.

### M-08. Нет обработки Reduce Motion для DisplayView

`CalculatorButton` использует `@Environment(\.accessibilityReduceMotion)` (строка 183), но `DisplayView` — анимации shake и flash работают независимо от настройки Reduce Motion пользователя.

### M-09. ClipboardManager и HistoryService — @unchecked Sendable

`HistoryService.swift` строка 3:
```swift
public final class HistoryService: @unchecked Sendable {
```

`ClipboardManager.swift` строка 8:
```swift
public final class ClipboardManager: @unchecked Sendable {
```

Это обходит проверку потокобезопасности компилятора. Хотя NSLock используется корректно, `@unchecked Sendable` скрывает потенциальные гонки данных от системы Swift Concurrency. SRS Section 87 требует использовать современную модель конкурентности Swift — предпочтительно `actor`.

### M-10. Нет обработки клавиши Tab / Shift+Tab

**SRS Section 68:**
> Поддерживаются: Tab, Shift+Tab

**Факт:** `KeyHandlerNSView.performKeyEquivalent` не обрабатывает Tab/Shift+Tab для навигации между кнопками.

### M-11. Нет ⌘A (выделить всё) и ⌘Z (отмена)

**SRS Section 68:**
> Поддерживаются: ⌘A, ⌘Z (если действие действительно можно отменить)

**Факт:** Не реализованы. `performKeyEquivalent` обрабатывает только ⌘C и ⌘V.

## 5. Незначительные замечания (Nice to Have)

### N-01. Ошибки в CalculatorError на английском, а не локализованные

Все сообщения в `CalculatorError.errorDescription` — на английском. SRS Section 34 требует понятных сообщений на языке пользователя.

### N-02. Hardcoded строка "Cannot evaluate" в ViewModel

`CalculatorViewModel.swift` строка 187:
```swift
errorMessage = "Cannot evaluate"
```
Должно использовать `NSLocalizedString("clipboard.cannotEvaluate", ...)`.

### N-03. AnyShape @unchecked Sendable

`CalculatorButton.swift` строки 254-261:
```swift
extension AnyShape: @unchecked Sendable {}
```
Обходит проверку Sendable для Shape. Безопасно в данном контексте, но не идеально.

### N-04. Нет обработки пустого буфера обмена при ⌘V

`CalculatorViewModel.insertFromClipboard()` строка 178 проверяет `!trimmed.isEmpty`, что хорошо. Но `KeyHandlerNSView.performKeyEquivalent` (строки 92-96) вызывает это только если `getString()` возвращает не-nil, что уже включает проверку пустоты. Двойная проверка — избыточна, но безвредна.

### N-05. Форматирование выражения в DisplayView: замена "." на ","

`DisplayView.swift` строка 108:
```swift
.replacingOccurrences(of: ".", with: ",")
```
Это работает для отображения, но если пользователь вставляет выражение с запятой как десятичным разделителем (например, из европейского калькулятора), оно не будет распознано. SRS Section 31 упоминает это как «желательно».

### N-06. Нет обработки ⌘= (равно)

SRS Section 69 говорит Enter/Return вычисляют выражение. Клавиша `=` на основной клавиатуре не обрабатывается отдельно, хотя `handleKeyCommand` в ViewModel (строка 167) её поддерживает. `performKeyEquivalent` не перехватывает ⌘=.

### N-07. HistoryPanelView вызывает getEntries() три раза при рендере

`HistoryPanelView.swift`:
- Строка 10: `HistoryService.shared.getEntries().isEmpty`
- Строка 18: `HistoryService.shared.getEntries()`
- Строка 48: `HistoryService.shared.getEntries().isEmpty`

Каждый вызов блокирует lock. Следует кэшировать результат в локальную переменную.

### N-08. Нет обработки выражений с очень большим количеством токенов

SRS Section 35 упоминает тестирование на выражениях >100 токенов. Нет явной защиты от бесконечной рекурсии при глубоко вложенных скобках (stack overflow).

### N-09. `formatter.format(dec)` в ViewModel использует locale-aware форматирование для внутреннего хранения

`CalculatorViewModel.swift` строки 32, 46:
```swift
expression = formatter.format(dec)
```
Это записывает локализованную строку (например, "1,5" для русской локали) обратно в `expression`. При последующей оценке `engine.evaluate(expression)` попытается распарсить запятую как часть числа, что может вызвать ошибку. SRS Section 31 говорит сохранять внутреннее представление независимым от локали.

## 6. Положительные находки (Что сделано хорошо)

### ✅ P-01. CalculatorEngine — полностью изолированный модуль

CalculatorEngine не имеет зависимостей от SwiftUI, AppKit, ViewModels или Services. Собирается и тестируется отдельно. Соответствует SRS Section 21.

### ✅ P-02. Decimal для всех вычислений

SRS Section 36 требует `Decimal`. Реализация использует `Decimal` повсеместно в Engine, Evaluator и AST. Тест `testEvaluate_DecimalAddition_NoRoundingError` подтверждает: `0.1 + 0.2 = 0.3` без артефактов.

### ✅ P-03. Собственный парсер (Shunting Yard)

SRS Section 24 запрещает NSExpression, JavaScriptCore, eval. Реализация использует собственный алгоритм сортировочной станции — Parser.swift строки 24-91.

### ✅ P-04. AST через indirect enum

`ExpressionNode.swift` — чистый `indirect enum`, как рекомендовано в SRS Section 22. Простой, понятный, легко тестируемый.

### ✅ P-05. Тестовое покрытие

| Модуль | Файл тестов | Кол-во тестов |
|--------|-------------|---------------|
| Tokenizer | TokenizerTests.swift | 27 |
| Parser | ParserTests.swift | 13 |
| Evaluator | EvaluatorTests.swift | 18 |
| Engine (интеграция) | CalculatorEngineTests.swift | 35 |
| UI | CalculatorUITests.swift | 10 |

**Итого:** ~103 теста. Покрытие всех специальных случаев из SRS Section 39.

### ✅ P-06. MVVM архитектура

Чёткое разделение: View → ViewModel → Engine/Services. View не содержит бизнес-логики, ViewModel не вычисляет, Parser не знает о UI. Соответствует SRS Section 17.

### ✅ P-07. Sendable для CalculatorEngine компонентов

`CalculatorEngine`, `Tokenizer`, `Parser`, `Evaluator`, `Token`, `ExpressionNode`, `NumberFormatterService` — все conform to `Sendable`. Соответствует SRS Section 23 (потокобезопасность).

### ✅ P-08. Обработка специальных форматов чисел

Шестнадцатеричные (`0xFF`), двоичные (`0b1010`), восьмеричные (`0o77`), экспоненциальная запись (`1.5e3`), разделители тысяч (`1,000,000`) — всё реализовано и протестировано.

### ✅ P-09. Константы π и e

Поддержка Unicode π (π), ASCII π ("pi"), и числа Эйлера ("e"). SRS Section 39 таблица.

### ✅ P-10. Обработка ошибок — структурированная

`CalculatorError` — enum с 10 случаями, все conform to `LocalizedError`. Нет stack traces пользователю. Соответствует SRS Section 34.

### ✅ P-11. Автовычисление при вводе

`tryAutoEvaluate()` в ViewModel автоматически вычисляет выражение по мере ввода (если не заканчивается оператором). Обеспечивает мгновенную обратную связь — ключевое требование UX SRS Section 66.

### ✅ P-12. KeyHandlerNSView — нативная обработка клавиатуры

Правильное использование `NSViewRepresentable` + переопределение `keyDown(with:)` и `performKeyEquivalent(with:)`. Поддержка numpad, ⌘C/V, Escape, Backspace, Enter/Return. Соответствует SRS Section 68.

### ✅ P-13. Анимации кнопок

Scale effect при нажатии (0.93x), DragGesture для press-detection, адаптация под Reduce Motion. Плавные переходы между режимами (standard/scientific — хотя сам режим должен быть удалён).

### ✅ P-14. Accessibility базовый уровень

`accessibilityLabel`, `accessibilityAddTraits(.isButton)`, `accessibilityIdentifier` на кнопках. VoiceOver label для дисплея. Соответствует SRS Section 83 (базово).

### ✅ P-15. История вычислений

HistoryService с ограничением в 50 записей, NSLock для потокобезопасности, HistoryPanelView с NavigationStack. Повторное использование записей через `useHistoryEntry()`. Соответствует SRS Section 75.

### ✅ P-16. Memory operations (MC/M+/M-/MR)

Реализованы в ViewModel и доступны в научном режиме (который должен быть удалён — см. C-01).

### ✅ P-17. Zero external dependencies

`Package.swift` не содержит внешних зависимостей. Только SwiftUI, Foundation, Observation, AppKit. Соответствует SRS Section 13.5.

### ✅ P-18. Двойная обработка "=" в конце выражения

Tokenizer удаляет trailing `=` (строка 135). SRS Section 39 таблица: `(15+16)/4=` → обрабатывается как `(15+16)/4`.

### ✅ P-19. Обработка многострочного ввода

Tokenizer обрезает по первой новой строке (строка 139). SRS Section 39 таблица: `15+16\n20+30` → обрабатывается только первая строка.

### ✅ P-20. Reject NaN и Infinity

Preprocess бросает `invalidExpression` для "NaN" и "Infinity". SRS Section 39 таблица.

## 8. Детальный анализ неучтённых нюансов реализации

### 8.1. Граничный случай: выражение "()" 

```
Tokenizer tokenize("()") → [.leftParenthesis, .rightParenthesis]
Parser toRPN: left paren pushed, right paren pops until left paren → stack empty
Then throws extraClosingParenthesis (line 40-43 Parser.swift)
```

**Результат:** `CalculatorError.extraClosingParenthesis` — корректно.

### 8.2. Граничный случай: выражение "(+5)"

```
Tokenizer → [.leftParenthesis, .unaryMinus, .number(5)]
Parser toRPN: number and unaryMinus go to output, left paren stays on stack
After loop: throws extraClosingParenthesis
```

**Результат:** Ошибка. Но математически `(−5)` — валидное выражение = −5.

### 8.3. Граничный случай: "5%+"

```
Tokenizer → [.number(5), .percent, .binaryOperator(.add)]
validateTokenSequence: binary operator at end — no next token check for trailing operator
Parser toRPN: output = [5, percent, +], stack empty after processing
buildAST: tries to pop 2 operands for +, but only 1 (5/100) on stack → throws invalidExpression
```

**Результат:** Ошибка — корректно.

### 8.4. Граничный случай: "e" как переменная vs константа

Если пользователь вводит `e` как часть переменной (например, `exp(2)`), то `p` будет распознан как `invalidCharacter`. Это ожидаемое поведение — калькулятор не поддерживает переменные.

### 8.5. Граничный случай: "0." (число с точкой в конце)

```
readNumber: numberStr = "." → line 216 returns (0, start)
```

**Результат:** Возвращает `(0, startIndex)` — токен не создаётся, индекс не продвигается. Это может привести к бесконечному циклу в main tokenize loop... но нет: `char == "."` обрабатывается в условии строки 83 (`if char.isNumber || char == "."`). readNumber вызывается и возвращает (0, start). Затем цикл продолжается с того же индекса — **бесконечный цикл**.

**ВНИМАНИЕ:** Это потенциальный баг. Выражение `"5+"` → после `+` идёт конец строки, что нормально. Но `"5."` → точка вызывает readNumber, которая возвращает (0, start) без продвижения индекса. Цикл `while i < cleaned.endIndex` повторяется бесконечно на той же позиции.

### 8.6. Граничный случай: "1..5" (две точки)

```
readNumber: first '.' sets hasDecimal = true, second '.' is skipped (hasDecimal check line 198)
numberStr = "1." → line 216 returns (0, start) — бесконечный цикл!
```

**ВНИМАНИЕ:** Тот же потенциальный бесконечный цикл. SRS Section 33 требует обнаруживать «несколько десятичных разделителей». Tokenizer имеет ошибку `multipleDecimalSeparators` в CalculatorError, но она **нигде не используется**.

### 8.7. Граничный случай: "1,,5" (разделитель тысяч с буквами)

```
preprocess: isThousandsSeparatorPattern checks all chars are digits or commas → "1,,5" passes
Result: removes commas → "15" — неверно! Должна быть ошибка.
```

**ВНИМАНИЕ:** `isThousandsSeparatorPattern` (строка 158-163) проверяет только что все символы — цифры или запятые. Он не проверяет валидность расположения запятых (например, "1,,5" или ",1000").

### 8.8. Граничный случай: "- -5" (два минуса подряд)

```
Tokenizer: first '-' → unaryMinus (tokens empty), second '-' → tokens.last is .unaryMinus → lastTokenIsOperatorOrLeftParen returns true → unaryMinus again
Tokens: [.unaryMinus, .unaryMinus, .number(5)]
Parser: buildAST applies two negations → +5. Результат верный, но двойной унарный минус — нестандартно.
```

### 8.9. Граничный случай: "0x" (hex без цифр)

```
readHex: hexStr = "" → UInt64("", radix: 16) returns nil → returns (0, start)
Бесконечный цикл — индекс не продвигается!
```

### 8.10. Граничный случай: "0b" (binary без цифр), "0o" (octal без цифр)

Аналогично hex — бесконечный цикл при отсутствии цифр после префикса.
