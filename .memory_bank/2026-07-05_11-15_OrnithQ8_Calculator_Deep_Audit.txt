## Executive Summary

Проект GateCalc представляет собой нативный калькулятор для macOS с поддержкой математических выражений и буфера обмена. Архитектура в целом соответствует MVVM, вычислительный движок реализован корректно с использованием алгоритма Shunting Yard и Decimal для точных вычислений.

**Критические проблемы:**
1. Прямое нарушение философии проекта — реализован научный режим с тригонометрией, логарифмами и другими запрещёнными функциями
2. Несоответствие визуальной спецификации (размеры, цвета, типографика)
3. Отсутствие локализации критических сообщений об ошибках
4. Наличие TODO в production-коде

**Положительные стороны:**
1. Вычислительный движок реализован корректно и полностью соответствует SRS
2. Используется Decimal для точных вычислений
3. Собственный парсер без внешних зависимостей
4. Хорошее покрытие тестами (Unit + UI)
5. Чистая архитектура с разделением ответственности

## 2. Несоответствия визуальной спецификации

### 2.1. Размеры окна (SRS Section 42)

**Статус: НЕСООТВЕТСТВИЕ**

SRS указывает:

**Реальность:** `CalculatorApp.swift:14`
```swift
.defaultSize(width: 340, height: 490)
```

Разница: -10pt по ширине, -30pt по высоте.

**Рекомендация:** Привести к 350x520 или обосновать отклонение.

### 2.2. Размеры кнопок (SRS Section 42, 57)

**Статус: НЕСООТВЕТСТВИЕ**

SRS указывает:
- Цифровые кнопки: квадратные, сторона 60 pt

**Реальность:** `CalculatorView.swift:19`
```swift
private var buttonDiameter: CGFloat { mode == .standard ? 66 : 48 }
```

Размер кнопок в стандартном режиме: 66pt вместо 60pt.

**Рекомендация:** Привести к 60pt или обосновать отклонение.

### 2.3. Типографика (SRS Section 42, 53)

**Статус: НЕСООТВЕТСТВИЕ**

SRS указывает:
- Текущее выражение: SF Pro, 18 pt
- Результат: SF Pro, 42 pt
- Ошибка: SF Pro, 24 pt

**Реальность:** `DisplayView.swift:17,31`
```swift
.font(.system(size: 18, weight: .regular, design: .rounded))  // выражение
.font(.system(size: 22, weight: .regular, design: .rounded))  // ошибка
```

`DisplayView.swift:94-98`:
```swift
case 0...9:   return .system(size: 70, weight: .thin,    design: .rounded)
case 10...12: return .system(size: 56, weight: .thin,    design: .rounded)
case 13...15: return .system(size: 44, weight: .light,   design: .rounded)
default:      return .system(size: 32, weight: .regular, design: .rounded)
```

Проблемы:
1. Используется `design: .rounded` вместо SF Pro (system font)
2. Размер результата варьируется от 32 до 70pt вместо фиксированных 42pt
3. Размер ошибки 22pt вместо 24pt

**Рекомендация:** Использовать системный шрифт без `.rounded` design, привести размеры к спецификации.

### 2.4. Цветовая система (SRS Section 42, 54)

**Статус: НЕСООТВЕТСТВИЕ**

SRS указывает использовать системные цвета:
- Фон калькулятора: systemGroupedBackground
- Фон цифровых кнопок: secondarySystemBackground
- Фон кнопок операций: systemGray5

**Реальность:** `CalculatorColors.swift`
```swift
static let background = Color(nsColor: .windowBackgroundColor)  // не systemGroupedBackground
static let buttonDigit = Color(light: ..., dark: ...)  // hardcoded RGB
static let buttonFunction = Color(light: ..., dark: ...)  // hardcoded RGB
```

**Рекомендация:** Использовать системные semantic colors согласно SRS.

### 2.5. Радиусы скругления (SRS Section 42, 58)

**Статус: НЕСООТВЕТСТВИЕ**

SRS указывает:
- Кнопки: 12 pt

**Реальность:** `CalculatorButton.swift` использует `.cornerRadius(diameter / 2)` что делает кнопки полностью круглыми, а не с радиусом 12pt.

**Рекомендация:** Использовать `.cornerRadius(12)` для кнопок.

## 3. Функциональные несоответствия

### 3.1. Обработка десятичного разделителя (SRS Section 31, 39)

**Статус: ПРОБЛЕМА**

SRS Section 31 указывает:
- Желательно учитывать локаль пользователя при вводе и отображении десятичного разделителя

SRS Section 39 указывает:
- `1,5` (в локали с запятой) → `1.5`

**Реальность:** `Tokenizer.swift:148-153`
```swift
if trimmed.contains(comma) {
    if !trimmed.contains(".") && isThousandsSeparatorPattern(trimmed) {
        result.removeAll(where: { $0 == comma })
    }
}
```

Проблема: код обрабатывает запятые только как разделители тысяч (когда все символы — цифры и запятые), но не обрабатывает случай "1,5" как десятичный разделитель.

**Рекомендация:** Добавить обработку запятой как десятичного разделителя в текущей локали.

### 3.2. Обработка константы "e" (SRS Section 39)

**Статус: ПРОБЛЕМА**

SRS Section 39 указывает поддержку "e" как константы Эйлера.

**Реальность:** `Tokenizer.swift:96-113`
```swift
if char == "e" {
    let nextIndex = cleaned.index(after: i)
    if nextIndex < cleaned.endIndex {
        let nextChar = cleaned[nextIndex]
        if nextChar.isNumber || nextChar == "." {
            let (number, newIndex) = readNumber(cleaned, from: i)
            tokens.append(.number(number))
            i = newIndex
        } else {
            tokens.append(.number(Self.eulerNumber))
            advance(&i, in: cleaned)
        }
    } else {
        tokens.append(.number(Self.eulerNumber))
        advance(&i, in: cleaned)
    }
}
```

Проблема: "e3" интерпретируется как число 1000 (e * 10^3), а не как ошибка. Хотя SRS не указывает явно, что "e" должно быть только отдельной константой, логично предположить, что "e3" должно быть ошибкой.

**Рекомендация:** Уточнить поведение или добавить валидацию.

### 3.3. Сохранение состояния (SRS Section 9, 79)

## 5. Архитектурные замечания

### 5.1. Нарушение принципа разделения ответственности (SRS Section 17)

**Статус: ЗАМЕЧАНИЕ**

SRS Section 17 требует:
- ViewModel не должен заниматься вычислениями

**Реальность:** `CalculatorViewModel.swift` напрямую вызывает `engine.evaluate()` в методах:
- `appendCharacter(_:)` (строка 38)
- `evaluate()` (строка 63)
- `tryAutoEvaluate()` (строка 209)

Хотя ViewModel не реализует алгоритмы вычисления, он координирует процесс и обрабатывает результаты. Это скорее архитектурный выбор, чем нарушение.

**Рекомендация:** Документировать, что ViewModel координирует вычисления, но не реализует их.

### 5.2. Singleton HistoryService (SRS Section 18)

**Статус: ЗАМЕЧАНИЕ**

SRS Section 18 требует не использовать глобальные Singleton без объективной необходимости.

**Реальность:** `HistoryService.swift` использует singleton pattern.

**Обоснование:** История вычислений — глобальное состояние приложения, singleton оправдан.

**Рекомендация:** Оставить как есть с документированным обоснованием.

### 5.3. @unchecked Sendable (SRS Section 87)

**Статус: ЗАМЕЧАНИЕ**

`ClipboardManager.swift:8` и `HistoryService.swift:3` используют `@unchecked Sendable`.

**Обоснование:** NSPasteboard и NSLock не являются Sendable по умолчанию, но используются корректно.

**Рекомендация:** Добавить комментарии с обоснованием.

## Заключение

Проект GateCalc имеет хорошую архитектурную основу и корректно реализованный вычислительный движок. Основные проблемы связаны с нарушением философии проекта (научный режим) и несоответствием визуальной спецификации.
