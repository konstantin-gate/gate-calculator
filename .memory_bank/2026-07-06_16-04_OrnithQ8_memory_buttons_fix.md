## 1. Анализ проблемы

### 1.1. Текущее состояние кода

**Файл:** `Sources/ViewModels/CalculatorViewModel.swift` (строки 131-149)

```swift
func memoryClear() {
    memoryValue = 0
}

func memoryAdd() {
    guard let val = resultDecimal else { return }
    memoryValue += val
}

func memorySubtract() {
    guard let val = resultDecimal else { return }
    memoryValue -= val
}

func memoryRecall() {
    expression = memoryValue.description
    result = nil
    errorMessage = nil
}
```

### 1.2. Выявленная ошибка

**Критическая проблема:** Метод `memoryRecall()` не сбрасывает свойство `resultDecimal`.

**Почему это важно:** Свойство `hasResult` (строка 19) вычисляется как `resultDecimal != nil`. Это свойство используется в методах `appendCharacter()` (строки 32-42) для определения поведения при вводе новых символов.

**Сценарий ошибки:**

1. Пользователь вычисляет `15 + 16 =` → результат `31`, `resultDecimal = 31`, `expression = ""`
2. Пользователь нажимает `M+` → `memoryValue += 31`, теперь `memoryValue = 31`
3. Пользователь вычисляет `10 + 5 =` → результат `15`, `resultDecimal = 15`, `expression = ""`
4. Пользователь нажимает `MR` → вызывается `memoryRecall()`:
   - `expression = "31"` (значение из памяти)
   - `result = nil`
   - `errorMessage = nil`
   - **НО `resultDecimal` остаётся равным `15`!**

5. Теперь состояние:
   - `expression = "31"`
   - `resultDecimal = 15` (устаревшее!)
   - `hasResult = true` (потому что resultDecimal != nil)

6. Пользователь нажимает `+` (оператор):
   - В `appendCharacter()` срабатывает ветка `hasResult && isOperator(char)` (строка 36)
   - Выполняется: `expression = dec.description` → `expression = "15+"`
   - **Ожидалось:** `expression = "31+"` (продолжение выражения из памяти)
   - **Получено:** `expression = "15+"` (используется устаревшее resultDecimal)

7. Пользователь вводит `20 =`:
   - Вычисляется `15 + 20 = 35`
   - **Ожидалось:** `31 + 20 = 51`

### 1.3. Дополнительные проблемы

**Проблема 2:** После `memoryRecall()` пользователь может неосознанно начать новый ввод, если нажмёт цифру:
- `hasResult = true` (из-за несброшенного resultDecimal)
- В `appendCharacter()` срабатывает ветка `hasResult && !isOperator(char)` (строка 32)
- Выполняется: `expression = ""; result = nil; resultDecimal = nil`
- **Результат:** выражение из памяти (`"31"`) теряется, начинается новый ввод

**Проблема 3:** Визуальное несоответствие:
- На дисплее отображается `expression = "31"` (из памяти)
- Но `hasResult = true`, что означает, что система считает, что есть результат вычисления
- Это может запутать пользователя при дальнейших операциях

### 1.4. Подтверждение ошибки через анализ кода

**Факт 1:** `hasResult` определяется как `resultDecimal != nil` (строка 19 CalculatorViewModel.swift)

**Факт 2:** `memoryRecall()` устанавливает только:
- `expression = memoryValue.description`
- `result = nil`
- `errorMessage = nil`

**Факт 3:** `memoryRecall()` НЕ устанавливает:
- `resultDecimal = nil` ← ЭТО ОШИБКА

**Факт 4:** В `appendCharacter()` (строки 29-48) логика полностью зависит от `hasResult`, которая зависит от `resultDecimal`

**Вывод:** После `memoryRecall()` состояние `resultDecimal` остаётся прежним, что приводит к несоответствию между отображаемым выражением и внутренним состоянием.

## 2. Архитектурное решение

### 2.1. Принцип исправления

**Единственное необходимое изменение:** Добавить сброс `resultDecimal = nil` в метод `memoryRecall()`.

**Обоснование:**
- `memoryRecall()` извлекает значение из памяти и помещает его в expression
- Это новое "начальное" состояние, аналогичное тому, что было бы после ввода числа
- `resultDecimal` должен быть nil, потому что выражение ещё не вычислено (оно только введено)
- `result` уже сброшен (строка 147), что корректно

### 2.2. Почему это единственное решение

**Альтернатива 1:** Изменить `hasResult` на проверку `result != nil` вместо `resultDecimal != nil`

**Почему не подходит:**
- `result` — это отформатированная строка для отображения
- `resultDecimal` — это сырое Decimal значение для вычислений
- Разделение этих понятий архитектурно верно (см. исправление C-08 в документации)
- Изменение `hasResult` нарушит логику автовычисления и других методов

**Альтернатива 2:** Изменить `appendCharacter()` для обработки случая, когда expression не пустое, но resultDecimal тоже не nil

**Почему не подходит:**
- Это замаскирует корневую проблему
- Приведёт к более сложной и запутанной логике
- Нарушит принцип единственной ответственности (SRP)

**Альтернатива 3:** Добавить визуальную индикацию наличия значения в памяти

**Почему не подходит (на данном этапе):**
- Это улучшение UX, а не исправление ошибки
- Не решает корневую проблему несоответствия состояния
- Может быть реализовано позже как отдельная задача

### 2.3. Подтверждение корректности решения

**Проверка 1:** После исправления `memoryRecall()`:
- `expression = memoryValue.description` (например, "31")
- `result = nil`
- `errorMessage = nil`
- `resultDecimal = nil` ← НОВОЕ

**Проверка 2:** `hasResult` будет `false` (потому что resultDecimal == nil)

**Проверка 3:** Поведение `appendCharacter()` после MR:
- Если пользователь нажмёт оператор (например, "+"):
  - `hasResult = false`, поэтому срабатывает только `expression += char` (строка 44)
  - `expression = "31+"` ← КОРРЕКТНО
- Если пользователь нажмёт цифру (например, "5"):
  - `hasResult = false`, поэтому срабатывает только `expression += char` (строка 44)
  - `expression = "315"` ← КОРРЕКТНО (продолжение ввода)

**Проверка 4:** Поведение других методов памяти:
- `memoryClear()`: не требует изменений, корректно сбрасывает только память
- `memoryAdd()`: работает корректно, добавляет resultDecimal к memoryValue
- `memorySubtract()`: работает корректно, вычитает resultDecimal из memoryValue

## 3. Детализированный план реализации

### 3.1. Шаг 1: Исправить метод `memoryRecall()`

**Файл:** `Sources/ViewModels/CalculatorViewModel.swift`  
**Строка:** 145-149

**Текущий код:**
```swift

    expression = memoryValue.description
    result = nil
    errorMessage = nil
}
```

**Новый код:**
```swift
func memoryRecall() {
    expression = memoryValue.description
    result = nil
    resultDecimal = nil  // ИСПРАВЛЕНИЕ: сброс resultDecimal для согласованности состояния
    errorMessage = nil
}
```

**Изменения:**
- Добавить строку `resultDecimal = nil` после `result = nil`

**Обоснование порядка:**
- Сначала сбрасываем `expression` (устанавливаем значение из памяти)
- Затем сбрасываем `result` (визуальное отображение)
- Затем сбрасываем `resultDecimal` (внутреннее состояние для вычислений)
- В конце сбрасываем `errorMessage` (ошибки быть не должно)

### 3.3. Шаг 3: Верификация сценариев использования

#### Сценарий 1: Базовое использование памяти

**Действия:**

2. Нажать `M+` → память = 31
3. Вычислить `10 + 5 =` → результат `15`
4. Нажать `MR` → на дисплее должно быть `31` (из памяти)
5. Нажать `+` → expression = "31+"
6. Ввести `20 =` → результат должен быть `51`

**Ожидаемое поведение после исправления:**
- После шага 4: `expression = "31"`, `resultDecimal = nil`, `hasResult = false`
- После шага 5: `expression = "31+"`, `resultDecimal = nil`
- После шага 6: вычисляется `31 + 20 = 51`, результат отображается корректно

#### Сценарий 2: MR без предварительного вычисления

**Действия:**
1. Ввести `15 + 16` (без нажатия =)

**Ожидаемое поведение после исправления:**
- После шага 2: `expression = "0"` (память пуста), `resultDecimal = nil`, `hasResult = false`
- Корректно, потому что память была сброшена при вводе выражения (неявно через tryAutoEvaluate)

#### Сценарий 3: MC после вычисления

**Действия:**

3. Результат на дисплее должен остаться `31`

**Ожидаемое поведение после исправления:**
- После шага 2: `memoryValue = 0`, но `resultDecimal = 31` (не изменился)
- Корректно, потому что MC очищает только память

#### Сценарий 4: M+ и M- с результатом

**Действия:**
1. Вычислить `10 + 5 =` → результат `15`
2. Нажать `M+` → память = 15
3. Вычислить `20 + 10 =` → результат `30`
4. Нажать `M-` → память = 15 - 30 = -15
5. Нажать `MR` → на дисплее должно быть `-15`

**Ожидаемое поведение после исправления:**
- После шага 5: `expression = "-15"`, `resultDecimal = nil`, `hasResult = false`
- Корректно

#### Сценарий 5: MR с последующим вводом цифры

**Действия:**

3. Вычислить `20 + 10 =` → результат `30`
4. Нажать `MR` → на дисплее должно быть `15` (из памяти)
5. Нажать `2` → на дисплее должно быть `152` (продолжение ввода)

**Ожидаемое поведение после исправления:**
- После шага 4: `expression = "15"`, `resultDecimal = nil`, `hasResult = false`
- После шага 5: `expression = "152"` (просто добавление цифры к expression)
- Корректно, потому что пользователь может продолжить ввод с числом из памяти

## 4. Проверка отсутствия побочных эффектов

### 4.1. Зависимости от `resultDecimal`

**Методы, использующие `resultDecimal`:**

1. **`hasResult` (строка 19):**
   ```swift
   var hasResult: Bool { resultDecimal != nil }
   ```
   - После исправления: после MR `hasResult = false` (корректно)

2. **`appendCharacter()` (строки 32-42):**
   ```swift
   if hasResult && !isOperator(char) { ... }
   else if hasResult && isOperator(char) { ... }
   ```
   - После исправления: после MR `hasResult = false`, поэтому эти ветки не срабатывают
   - Корректно, потому что expression содержит число из памяти, а не результат вычисления

3. **`appendOperator()` (строки 54-60):**
   ```swift
   if hasResult {
       if let dec = resultDecimal { expression = dec.description + op }
   }
   ```
   - После исправления: после MR `hasResult = false`, поэтому эта ветка не срабатывает
   - Корректно, потому что метод оставлен для совместимости и не вызывается из UI

4. **`backspace()` (строки 97-108):**
   ```swift
   if expression.isEmpty, resultDecimal != nil { clear(); return }
   ```
   - После исправления: после MR `expression` не пустое (содержит значение из памяти), поэтому эта ветка не срабатывает
   - Корректно, потому что backspace должен удалять символы из expression

5. **`toggleSign()` (строки 112-127):**
   ```swift
   if expression.isEmpty {
       if let val = resultDecimal { ... }
   }
   ```
   - После исправления: после MR `expression` не пустое, поэтому эта ветка не срабатывает
   - Корректно, потому что toggleSign должен инвертировать знак текущего выражения

### 4.2. Зависимости от `expression`

**Методы, использующие `expression`:**

1. **`evaluate()` (строки 69-85):**
   ```swift
   let trimmed = expression.trimmingCharacters(in: .whitespaces)
   guard !trimmed.isEmpty else { return }
   ```
   - После MR: `expression` содержит значение из памяти, поэтому evaluate вычислит его
   - Корректно

2. **`tryAutoEvaluate()` (строки 207-218):**
   ```swift
   let trimmed = expression.trimmingCharacters(in: .whitespaces)
   guard !trimmed.isEmpty, !isTrailingOperator(expression) else { return }
   ```
   - После MR: `expression` содержит число, поэтому tryAutoEvaluate не вызывается (нет оператора)
   - Корректно

3. **`backspace()` (строки 102-104):**
   ```swift
   if !expression.isEmpty { expression.removeLast(); tryAutoEvaluate() }
   ```
   - После MR: `expression` не пустое, поэтому backspace удалит последний символ
   - Корректно

### 4.3. Зависимости от `result`

**Методы, использующие `result`:**

1. **DisplayView:** отображает `viewModel.result`
   - После MR: `result = nil`, поэтому на дисплее будет только expression
   - Корректно, потому что expression содержит значение из памяти

2. **`copyResult()`:** копирует `result` в буфер обмена
   - После MR: `result = nil`, поэтому копирование не выполнится
   - Корректно, потому что пользователь должен сначала вычислить выражение

## 9. Обоснование выбора решения

### 9.1. Почему именно это решение

**Критерий 1: Минимальность изменений**
- Изменяется только один метод (`memoryRecall()`)
- Добавляется одна строка кода
- Не затрагиваются другие методы и компоненты

**Критерий 2: Корректность**
- Исправляет корневую причину проблемы (несоответствие состояния)
- Не замаскировывает симптом, а устраняет его причину
- Сохраняет архитектурную целостность (разделение result и resultDecimal)

**Критерий 3: Предсказуемость**
- Поведение после исправления полностью определено и проверено
- Нет побочных эффектов на другие методы
- Согласовано с логикой `appendCharacter()` и другими методами

**Критерий 4: Соответствие документации**
- Исправление согласовано с описанием в Technical_Documentation.md (раздел 5)
- Документация указывает, что `memoryRecall()` устанавливает expression и сбрасывает result
- Добавление сброса resultDecimal логически вытекает из этого описания

### 9.2. Что не изменяется

- Методы `memoryClear()`, `memoryAdd()`, `memorySubtract()` остаются без изменений
- Логика `appendCharacter()` не изменяется
- Архитектурное разделение `result` (строка) и `resultDecimal` (Decimal) сохраняется
- Визуальное отображение на дисплее не изменяется (использует те же свойства)

**Минимизация:** Исправление не меняет публичный API, только внутреннее состояние. Все методы остаются теми же.
