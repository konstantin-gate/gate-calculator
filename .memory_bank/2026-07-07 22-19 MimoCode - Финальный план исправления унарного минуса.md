### 0.3. Три корневые причины

**Причина 1 (главная): Неверный приоритет унарного минуса в Shunting Yard**

Файл `Sources/CalculatorEngine/Parser/Precedence.swift:26-37`:
```swift
var precedenceValue: Int {
    switch self {
    case .binaryOperator(let op):
        return op.precedence.rawValue
    case .percent:
        return 2
    case .unaryMinus:
        return 2   // ← ПРОБЛЕМА: такой же как у * и /
    default:
        return 1
    }
}
```

Значение `precedenceValue` для `.unaryMinus` равно `2`, что совпадает с приоритетом `*`/`/` (тоже `2`). Enum `Precedence` объявлен с `rawValue = 3` для `.unaryMinus` (строка 6), но computed property `precedenceValue` **игнорирует это** и возвращает `2`.

**Как это ломает `5*-3`:** В алгоритме Shunting Yard (файл `Sources/CalculatorEngine/Parser/Parser.swift:42-52`), когда парсер встречает `unaryMinus` после `*`:
1. `top` в стеке = `*` (приоритет 2)
2. `token` = `unaryMinus` (приоритет 2)
3. Условие `top.precedenceValue == token.precedenceValue && top.isLeftAssoc` → `(2 == 2 && true)` = `true`
4. `*` выталкивается в output **до** помещения `unaryMinus` в стек
5. RPN получается `[5, *, unaryMinus]` — невалидный (бинарный оператор `*` получает только один операнд)
6. `buildAST` бросает `CalculatorError.invalidExpression`

**Причина 2: Токенизатор отвергает `unaryMinus` после `leftParenthesis`**

Файл `Sources/CalculatorEngine/Tokenizer/Tokenizer.swift:346-355`:
```swift
case .unaryMinus:
    let prevIsOp = i > tokens.startIndex && isOperatorOrLeftParen(tokens[i - 1])
    let prevIsBinaryOp: Bool = {
        guard i > tokens.startIndex else { return false }
        if case .binaryOperator(_) = tokens[i - 1] { return true }
        return false
    }()
    if prevIsOp && !prevIsBinaryOp {
        throw CalculatorError.doubleOperator
    }
```

Функция `isOperatorOrLeftParen` (строка 369-376) возвращает `true` для `.leftParenthesis`. Поэтому `(-3)` → `unaryMinus` после `leftParenthesis` → `prevIsOp = true`, `prevIsBinaryOp = false` → `true && !false = true` → ошибка `doubleOperator`.

**Причина 3: `tryAutoEvaluate` показывает ошибки при наборе неполных выражений**

Файл `Sources/ViewModels/CalculatorViewModel.swift:244-255`:
```swift
private func tryAutoEvaluate() {
    let trimmed = expression.trimmingCharacters(in: .whitespaces)
    guard !trimmed.isEmpty, !isTrailingOperator(expression), !hasUnclosedParentheses(trimmed) else { return }

    do {
        let value = try engine.evaluate(expression)
        result = formatter.format(value)
        resultDecimal = value
    } catch {
        errorMessage = error.localizedDescription   // ← ПРОБЛЕМА
    }
}
```

Метод вызывается из `appendCharacter()` (строка 76-78) и `backspace()` (строка 135) после каждого нечислового символа. Если выражение невалидно (например, `5*-` при наборе), ошибка устанавливается и мелькает на экране до следующего символа.

### 1.4. Обоснование

```swift
    case addition = 1
    case multiplication = 2
    case unaryMinus = 3

}
```

Raw value для `.unaryMinus` уже равен `3`. Computed property `precedenceValue` должен возвращать `3`, чтобы Shunting Yard корректно обрабатывал унарный минус как операцию с более высоким приоритетом, чем умножение/деление. Математически верно: `5*-3 = 5*(-3)`, а не `(5*)-3`.

### 1.5. Верификация через трассировку Shunting Yard для `5*-3`

```
Токены: [number(5), binaryOperator(.multiply), unaryMinus, number(3)]

После изменения precedenceValue для unaryMinus = 3:

1. number(5) → output: [5], stack: []

2. binaryOperator(.multiply):
   stack пуст → push *
   output: [5], stack: [*]

3. unaryMinus (precedenceValue = 3):
   top = *, precedenceValue(*) = 2
   Условие выталкивания: "top.precedenceValue > token.precedenceValue"
     → 2 > 3 = false ✗
   Условие: "top.precedenceValue == token.precedenceValue && top.isLeftAssoc"
     → 2 == 3 = false ✗
   → break, push unaryMinus
   output: [5], stack: [*, unaryMinus]

4. number(3) → output: [5, 3], stack: [*, unaryMinus]

Остаток стека (pop all):
   pop unaryMinus → output: [5, 3, unaryMinus]
   pop *          → output: [5, 3, unaryMinus, *]

RPN = [5, 3, unaryMinus, *]

buildAST(from: [5, 3, unaryMinus, *]):
    number(5)     → stack: [.number(5)]
    number(3)     → stack: [.number(5), .number(3)]
    unaryMinus    → pop .number(3) → .unaryMinus(.number(3))
                    stack: [.number(5), .unaryMinus(.number(3))]
    binaryOperator(.multiply):
      guard stack.count >= 2 → 2 >= 2 ✓
      right = .unaryMinus(.number(3))
      left  = .number(5)
      → .binary(.multiply, .number(5), .unaryMinus(.number(3)))

Evaluator: multiply(5, unaryMinus(3)) = 5 * (-3) = -15 ✅
```

### 1.7. Верификация: выражения `5++3`, `%*5`, `*-5` остаются ошибками

**`5++3`:** Проверяется в `case .binaryOperator` (строка 329-335), не затронута. `prevIsOp` для второго `+` = `true` → ошибка.

**`%*5`:** Проверяется в `case .percent` (строка 337-344). `prevIsOp` для `%` после `*` = `true` → ошибка.

**`*-5`:** Токенизируется как `[binaryOperator(*), unaryMinus, number(5)]`. Проверяется в `case .binaryOperator` для `*`: `prevIsOp` — нет предыдущего токена или предыдущий не оператор → `prevIsOp = false`. `nextIsOp = true` (unaryMinus), `nextIsUnaryMinus = true` → условие `nextIsOp && !nextIsUnaryMinus` = `true && false` = `false` → пропускается. **Но это невалидное выражение** — `*` без левого операнда. Это будет поймано на уровне парсера: `buildAST` при обработке `*` не найдёт достаточно операндов в стеке → `CalculatorError.invalidExpression`. ✅

### 2.3. Новый код

```swift
case .unaryMinus:

    let prevIsBinaryOp: Bool = {
        guard i > tokens.startIndex else { return false }
```

### 2.4. Обоснование

Текущее условие `prevIsOp && !prevIsBinaryOp` отвергает `unaryMinus` после `leftParenthesis`, потому что:
- `isOperatorOrLeftParen(.leftParenthesis)` = `true` → `prevIsOp = true`
- `leftParenthesis` не является `binaryOperator` → `prevIsBinaryOp = false`
- `true && !false = true` → ошибка

Но `(-3)` — абсолютно валидная математическая конструкция. Нужно добавить проверку: если предыдущий токен — `leftParenthesis`, то `unaryMinus` после него допустим.

```
     → NOT проверяется в case .percent (проверяется prevIsOp)
```

### 3.3. Новый код

```swift
private func tryAutoEvaluate() {
    let trimmed = expression.trimmingCharacters(in: .whitespaces)
    guard !trimmed.isEmpty, !isTrailingOperator(expression), !hasUnclosedParentheses(trimmed) else { return }

    do {
        let value = try engine.evaluate(expression)
        result = formatter.format(value)
        resultDecimal = value
    } catch {
        // Ошибки автовычисления не показываются пользователю —
        // выражение в процессе набора может быть неполным.
        // Ошибки отображаются только при явном нажатии "=" (метод evaluate()).
    }
}
```

### 3.4. Обоснование

**Цепочка вызовов (верифицировано через read):**
1. `CalculatorView.handleButtonPress` → `viewModel.appendCharacter(label.inputValue)` — вызов из View
2. `CalculatorViewModel.appendCharacter` (строка 60-79): в строке 61 вызывается `clearError()`, затем в строках 76-78 — `tryAutoEvaluate()`
3. `CalculatorViewModel.backspace` (строка 125-139): в строке 126 вызывается `clearError()`, затем в строке 135 — `tryAutoEvaluate()`
4. `CalculatorViewModel.useHistoryEntry` (строка 230-235): в строке 234 — `tryAutoEvaluate()`

**Почему пустой catch корректен:**
- `appendCharacter` и `backspace` — методы набора выражения. Выражение в процессе ввода неполное, ошибки неинформативны
- `useHistoryEntry` — загрузка из истории. Выражение из истории должно быть валидным, ошибки не нужны
- Метод `evaluate()` (строка 97-116, вызывается при нажатии `=`/Enter) **остаётся единственным местом** показа ошибок пользователю
- `clearError()` в начале `appendCharacter` и `backspace` очищает ошибку перед каждым вызовом `tryAutoEvaluate`, поэтому предложение Qwen36 (`if errorMessage == nil`) неэффективно — `errorMessage` уже `nil` на момент вызова
